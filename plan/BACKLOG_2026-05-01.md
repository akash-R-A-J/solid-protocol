## Tier 1 -- Hard mainnet blockers

Cannot deploy to mainnet without these. Everything in this tier is
either a soundness bypass we're knowingly running today
(`sec007-skip-onchain`) or a missing structural guarantee (multi-party
ceremony, multisig authorities, cross-VK replay protection).

### 1. SOLID-SEC-012 -- Multi-party trusted-setup ceremony

- **What.** Replace the single-party setup at `circuits/scripts/setup.js`
  (timestamp-entropy initial randomness) with a Powers-of-Tau-style
  multi-party ceremony. Each contributor adds their entropy and
  publishes a signed transcript; the toxic waste is destroyed by every
  honest contributor; soundness holds if at least one is honest.
- **Engineering time.** ~1 week of prep (ceremony tooling, contributor
  onboarding doc, transcript verification CI gate).
- **Calendar time.** **4-6 weeks** (longest pole on the path to mainnet).
  Coordinator + >=3 contributors + signed transcript + IPFS/Arweave
  artifact pinning.
- **Path.** Use snarkjs's standard Phase-1 + Phase-2 ceremony script.
  Coordinator publishes initial Phase-2 transcript; each contributor
  pulls, contributes, signs, pushes; final transcript becomes the new
  canonical zkey + VK. Pin sha256 in `circuits/build/verification_key.sha256`.
- **Depends on.** Tier 1 circuit changes (SEC-048 Option B, SEC-006 Part 2,
  SEC-051) need to land BEFORE the ceremony so the circuit is final.

### 2a. SOLID-SEC-048 Option B -- Registration-time BJJ subgroup proof (REVISED 2026-05-01)

> **Spec correction.** The earlier wording around `[8]*P == P` was
> wrong: `[8]*P` does NOT equal `P` for prime-order subgroup points.
> The correct invariant is `on_curve(P) AND P != (0,1) AND [r]*P == (0,1)`
> where `r = 2736030358979909402780800718157159386076813972158567259200215660948447373041`
> is the BJJ subgroup prime order (`(0,1)` is the Edwards identity).
> Constraint estimate also revised: ~3-3.5K (NOT ~30K) -- one
> constant-scalar mul over a 251-bit scalar via `BabyDbl` + `BabyAdd`
> primitives, plus on-curve + non-identity gates.

- **What.** Add a small dedicated Groth16 circuit
  (`circuits/bjj_subgroup_proof.circom`) with public inputs `(Ax, Ay)`
  enforcing the corrected subgroup invariant.  `register_issuer`
  consumes a Groth16 proof of this circuit alongside the candidate
  pubkey; on-chain Groth16 verify is the registration-time gate.
  Invalid keys never enter the registry.  Bypass dropped entirely.
- **Engineering time.** **1-2 weeks**.
- **Calendar time.** Batches with the SEC-012 ceremony (a separate
  Phase-2 of the existing PTAU; same contributor pool).  TWO
  ceremonies for mainnet: one for the main batch circuit (with
  SEC-006 Part 2 + SEC-051), one for the subgroup circuit -- but
  ONE shared PTAU and ONE shared contributor session.
- **Path.**
  1. **Spec lock first.** Correct registry/roadmap/BACKLOG language
     to the `[r]*P == identity` form (DONE 2026-05-01).
  2. **Isolated circuit + tests.** Write
     `circuits/bjj_subgroup_proof.circom` standalone with public
     inputs `(Ax, Ay)`; assert curve eq + non-identity + 251-bit
     constant-scalar mul by r yields identity.  Mocha test cases:
     Base8 accepts; honest Rust-generated key accepts; identity
     `(0,1)` rejects; order-2 `(0,-1)` rejects; off-curve rejects;
     torsion-tainted `P+T` rejects; proof for key A NOT reusable
     for key B.
  3. **Compile + measure constraints + sanity-check before any
     trusted setup.**  Constraint count must fit existing PTAU
     capacity (131K) -- 3.5K << 131K so this should hold trivially.
  4. **Trusted setup for the subgroup circuit.**  Reuse existing
     `circuits/trusted_setup/pot_final.ptau`; new Phase-2 produces
     `circuits/build/bjj_subgroup_proof.zkey` +
     `circuits/build/bjj_subgroup_verification_key.json` +
     `circuits/build/bjj_subgroup_verification_key.sha256`.
  5. **On-chain plumbing.**  New ix flow under
     `programs/issuer-registry/src/lib.rs`:
     - Either `register_issuer` directly accepts the proof
       (preferred for atomicity), OR a separate
       `init_subgroup_vk` + `store_subgroup_vk_chunk` +
       `finalize_subgroup_vk` mirroring the zk-verifier's VK
       upload pattern, with `register_issuer` reading from the
       finalized VK.
     - On-chain Groth16 verify reuses existing alt_bn128 syscall
       infrastructure.  Reconstruct public inputs from the supplied
       `(bjj_pub_key_x, bjj_pub_key_y)` (already canonical-encoded
       by SEC-062 gate).
     - On verify success: existing register_issuer logic (init
       account, etc.).  On verify failure: reject with new
       `ErrorCode::InvalidSubgroupProof`.
  6. **Drop `sec007-skip-onchain`.**  Remove the Cargo feature, the
     bypass arm, the `Sec007Bypass` event, and runbook references
     (CLAUDE.md, AGENTS.md, docs/DEPLOYMENT_AND_TESTING.md).
  7. **SDK + script updates.**
     - `ts-sdk/packages/issuer/src/index.ts`: new helper
       `generateSubgroupProof(bjj_pub_key)` that calls snarkjs
       against the small zkey/wasm.
     - `scripts/bootstrap_issuer.ts`: generate proof + pass it to
       `register_issuer`.
     - `ts-sdk/packages/core/src/index.ts::isInPrimeOrderSubgroup`
       stays as a UX/pre-submit gate; doc-comment updated to say
       "no longer load-bearing".
  8. **Tests + CI gates.**
     - Real-validator integration test: honest registration
       succeeds.
     - Invalid-subgroup-proof registration fails AND no issuer
       account is initialized.
     - Proof/key mismatch fails.
     - CI rejects any build that re-introduces
       `sec007-skip-onchain` (script grep gate).
     - CU baseline updated in `tests/cu_baselines.json`
       (`RegisterIssuer` ~365-400K).
  9. **Full e2e to `verified: true`.**
- **Soundness contract.** A malicious caller submitting a
  non-subgroup pubkey to `register_issuer` cannot produce a valid
  Groth16 proof of `[r]*P == identity` for that pubkey -- on-chain
  verify rejects.  The off-chain SDK predicate becomes
  defense-in-depth (UX), no longer load-bearing.
- **Risk.** Highest of any item in this tier.  Circuit changes
  cascade through:
  - The host-side public-input contract (subgroup circuit only --
    main batch circuit is untouched by SEC-048).
  - WASM bridge bytes (subgroup proof generation off-chain).
  - VK pinning artefacts (a NEW pin file for the subgroup VK).
  - On-chain ix surface (bigger `register_issuer` payload).
  Land this with **no workarounds**: if any phase fails, debug the
  root cause per L1 (cascade is the diagnostic) and fix forward;
  do NOT re-introduce the bypass.
- **Why a separate circuit, not in-batch.** Three reasons:
  (a) registry state itself becomes the trust set ("every
  registered issuer has a subgroup-validated key"), readable in
  isolation by auditors;
  (b) per-credential proving cost stays unchanged forever (no
  10-15% tax on every proof);
  (c) clean Option C (syscall) migration -- the syscall replaces
  just this small circuit's on-chain verify; main batch circuit
  doesn't move.

### 2b. SOLID-SEC-048 Option C -- Upstream `sol_babyjubjub_*` syscall (parallel track)

- **What.** Propose a Solana SIMD adding `sol_babyjubjub_*` syscalls
  (subgroup check, point-on-curve, scalar mul) so the on-chain check
  costs ~0 CU. Long-term cleanest fix.
- **Engineering time.** ~2 weeks (RFC + reference implementation in
  agave-validator + benchmark + security review request).
- **Calendar time.** **6-12 months** through Solana governance + a
  validator-network upgrade. Out of our control beyond the proposal.
- **Path.**
  1. Draft SIMD with motivation, semantics, gas pricing.
  2. Prototype the syscall in agave-validator using arkworks/curve25519-dalek-style
     constant-time scalar mul over BN254's twisted-Edwards form.
  3. Submit for Anza review; iterate.
  4. Once shipped on mainnet, swap zk-verifier from the in-circuit
     gate (Option B) to the syscall: removes ~30K constraints from the
     circuit, lowers proving time, reduces VK size.
- **Run in parallel** to Option B; Option B ships v1, Option C ships
  v1.x. Both are proper fixes (no workarounds) -- the difference is
  cost per verify.
- **Tracking.** Open `parallel-track` checkbox under SEC-048 in
  `sec/SECURITY_REGISTRY.md`; add a Phase 5 P0 entry in
  `docs/FORWARD_ROADMAP.md` separating "ship Option B" from "advance
  Option C SIMD".

### 4. SOLID-SEC-006 Part 2 -- Bind `vk_generation` into circuit public inputs

- **What.** Currently `verifier_config.vk_generation` is on-chain only;
  the circuit doesn't bind it, so an attacker with cached proofs from
  generation N could replay them after rotation to generation N+1
  (modulo the freeze-gate timelock). Bind it as public-input slot 32
  (`NR_PUBLIC_INPUTS = 32 -> 33`).
- **Engineering time.** **0.5 week**.
- **Calendar time.** Batches with the SEC-012 ceremony.
- **Path.**
  1. Add `vkGeneration` input to `batch_credential_query.circom`,
     expose as the 33rd public input.
  2. Re-run trusted setup (batches with #2a + #5).
  3. Update `programs/zk-verifier/src/lib.rs`:
     - `NR_PUBLIC_INPUTS = 33`
     - new `VK_GENERATION_INPUT_INDEX = 32`
     - reconstruct slot 32 from `verifier_config.vk_generation` on-chain
       (treat as account-derived, not wire-derived).
  4. Update WIRE_INPUT_SLOTS so vk_generation is NOT on the wire; this
     is intentional -- the verifier config is the source of truth.
  5. Update holder SDK `generateBatchProof` to pass `vk_generation` as
     a circuit input; SDK reads the on-chain `verifier_config` to
     learn the current generation.

### 11b. Credential delivery / secure transport (issuer -> holder)

- **What.** Today's e2e hands credentials from `issue.ts` to
  `prove.ts` via the local `$TMPDIR/solid-e2e-<uid>/state.json`
  file (mode 0600).  That's test-only -- for production devnet
  user-testing, the issuer is a separate party from the holder
  and the credential plaintext (data + EdDSA signature) needs a
  real transport channel.  `docs/SYSTEM_VISION.md` Section 2.2
  designs three (HTTPS+OAuth portal, encrypted DM via Curve25519
  derived from holder's Solana seed, QR code with TTL); none are
  implemented.  `docs/system_architecture.md` references
  `deliverToHolder()` but no such function exists in
  `@solid-protocol/issuer` -- **doc-vs-code drift flagged in
  E2E_BLOCKERS.md Section O5**.
- **Engineering time.** **1-2 weeks** for the MVP (Phase 0: HTTPS
  portal); **3-4 weeks** for the full encrypted-DM track.
- **Path (Phase 0 -- devnet-ready MVP).**
  1. New package `@solid-protocol/issuer-gateway` (or extension of
     `@solid-protocol/issuer`):
     - `encryptCredentialFor(credential, holderCurve25519PubKey) -> EncryptedEnvelope`
       (XChaCha20-Poly1305 with ephemeral X25519 ECDH).
     - `deliverViaPortal(envelope, deliveryUrl) -> DeliveryReceipt`
       (POST to issuer-hosted URL; holder retrieves via wallet-signed
       session token).
  2. Reference issuer portal: minimal HTTPS service (Next.js or
     similar) that stores envelopes keyed on holder pubkey + a
     short TTL.
  3. Holder SDK: `fetchCredentialsFor(walletPubkey, portalUrl)`
     pulls all envelopes, decrypts using wallet-derived
     Curve25519 key, hands plaintext to existing `StoredCredential`
     flow.
  4. ADR: open the next slot after ADR-0015 ("Credential delivery
     and secure transport").
- **Mainnet blocker.** No (production readiness, not soundness).
- **Devnet blocker for real-user testing.** **YES.**  Without this,
  we can't onboard real issuers + real holders on devnet --
  Phase 0 is the minimum to enable a useful demo.
- **Security contract.**
  - Confidentiality: encrypted envelope; only target holder can
    decrypt.
  - Authenticity: envelope signed by issuer's Solana wallet (or
    BJJ key for cross-verification with the on-chain commitment).
  - Anti-replay: TTL + single-use delivery URL.
  - Compromise of one transport reveals one credential, never the
    issuer's BJJ signing key.

## Discipline reminders for this arc

These are not new -- they are quoted from `plan/RESUME.md` Learnings
log because they apply directly:

- **L1.** If a fix bounces ("change X, then Y breaks, then Z breaks"),
  stop editing. Find the one definition whose wrongness produces the
  cascade and fix that.
- **L2.** Programs and circuits are the source of truth. Hierarchy:
  programs/circuits > crates > WASM bridge + TS SDK > scripts.
- **L3.** If the contract is wrong, fix the contract. No workarounds,
  no regressions. Encode invariants in the type system.
- **L4.** Add unit + integration tests + targeted msg! logs as part of
  the fix, not after. A fix without a regression gate has not shipped.
- **L7.** Before touching anything that interacts with a hard wire-size
  or CU cap, write down the byte / CU ledger explicitly UP-FRONT.
- **L8.** Separate "what I observed" from "why I think it happened".
  Don't lead with the speculative root-cause story when the fix is
  empirical.
- **L9.** When fixing a primary defect surfaces N latent bugs, each
  latent-bug fix is its own atomic commit + own regression gate + own
  registry entry. Do not bundle.

When stuck, re-read the matching learning and recent session log
(`plan/SESSION_LOG_2026-04-29.md`, `plan/SESSION_LOG_2026-04-30.md`)
before pivoting -- the same shape of problem has likely been solved.
