## Executive assessment

SolID is now a real, coherent private identity protocol implementation rather
than an aspirational scaffold.  The happy path has crossed the most important
practical threshold: a localnet run reached `verified: true` on-chain through
`verify_batch_proof_v2`, with replay rejection and measured CU baselines.  The
recent fixes also closed several issues that would have made that success
misleading: G2 byte ordering, proof wire size, root hash-family mismatch,
stale issuer-tree paths, unfinalized VK deployments, and SDK false-positive
verification.

My opinion: the system is technically strong and unusually well-documented for
an early privacy protocol, but it is still pre-mainnet.  It is a devnet
candidate, not a production launch candidate.  The remaining work is not
cosmetic; it is ceremony discipline, authority hardening, complete behavioral
tests, and one major cryptographic/CU design decision around BabyJubJub
subgroup enforcement.

## What is done

### 1. End-to-end proof path is real

The verifier now has a practical transaction shape:

- `NR_PUBLIC_INPUTS = 32`, post ADR-0014, in
  `programs/zk-verifier/src/lib.rs:60`.
- `NR_WIRE_INPUTS = 21`, with 11 public inputs reconstructed from accounts, in
  `programs/zk-verifier/src/lib.rs:65`.
- `verify_batch_proof_v2` reads a staged proof buffer, reconstructs roots,
  verifies Groth16, initializes the nullifier PDA, and closes the buffer in
  `programs/zk-verifier/src/lib.rs:752`.
- The SDK mirrors the 21-wire-input contract in
  `ts-sdk/packages/verifier/src/index.ts:47`.
- Proof-buffer payload assembly and chunked upload live in
  `ts-sdk/packages/verifier/src/index.ts:288` and
  `ts-sdk/packages/verifier/src/index.ts:695`.

This closes the old B13/SOLID-SEC-054 wall where the original
`verify_batch_proof` instruction could not fit Solana's packet limit.

### 2. Verifier trust-root reconstruction is materially stronger

The verifier no longer trusts caller-supplied roots for the main trust
anchors.  It reconstructs:

- `globalRoot` from `GlobalStateBinding`, owner-checked against
  `SCHEMA_REGISTRY_ID`, in `programs/zk-verifier/src/lib.rs:494`.
- `issuerTreeRoot` from `IssuerTreeBinding`, owner-checked against
  `ISSUER_REGISTRY_ID`, in `programs/zk-verifier/src/lib.rs:509`.
- Per-schema roots and hashes from active `SchemaTreeBinding` accounts in
  `programs/zk-verifier/src/lib.rs:543`.
- `verifierAddress` from the verifier program ID, removing caller control over
  the slot.

The accounts structs also seed-gate the global binding and issuer binding
PDAs with `seeds::program`, reducing the surface for account substitution:
`programs/zk-verifier/src/lib.rs:1217` and
`programs/zk-verifier/src/lib.rs:1242`.

### 3. Issuer revocation and cooldown now update proof soundness

The issuer tree is now the live revocation universe for proofs:

- The circuit proves issuer-tree membership against public input
  `issuerTreeRoot` in `circuits/batch_credential_query.circom:271`.
- Issuer leaves bind Solana authority, BJJ signing key, status epoch, and
  revocation nonce in `circuits/batch_credential_query.circom:300`.
- Atomic issuer update paths recompute Poseidon roots on-chain instead of
  writing caller-supplied roots.
- `revoke_issuer_atomic` and `request_withdrawal_atomic` now reject stale
  caller paths before the SPL Account Compression CPI through
  `verify_issuer_binding_anchor`, implemented in
  `programs/issuer-registry/src/lib.rs:167`.

This is the key recent close-out beyond the previous audit synthesis:
SOLID-SEC-077 fixed the stale-path / concurrent-root surface by anchoring the
caller path to `IssuerTreeBinding.current_root` before the CPI.  The follow-on
slot monotonicity fix in `write_issuer_tree_binding_root` closes the same-slot
last-writer-wins race at `programs/issuer-registry/src/lib.rs:119`.

### 4. VK freeze-gate is now operational, not just present on-chain

The zk-verifier program had freeze/rotation primitives, but prior deployment
scripts could leave `vk_finalized=false`.  The current working tree fixes this:

- `finalize_verification_key` sets `vk_finalized=true` in
  `programs/zk-verifier/src/lib.rs:280`.
- `store_verification_key` rejects writes after finalization in
  `programs/zk-verifier/src/lib.rs:228`.
- `scripts/initialize.ts` now finalizes after chunk upload and asserts the
  post-condition; see `scripts/initialize.ts:518` and
  `scripts/initialize.ts:595`.
- The same script now self-heals a stale local state cache when a validator
  reset leaves cached state pointing at absent on-chain accounts; see
  `scripts/initialize.ts:238` and `scripts/lib/e2e_state.ts:100`.

This closes SOLID-SEC-078 and makes SOLID-SEC-006 Part 1 meaningful in actual
deployments.

### 5. CU regression coverage exists

The prior synthesis audit noted a doc/code contradiction around the CU gate.
That contradiction is fixed in the current tree:

- `.github/workflows/ci.yml:532` runs `python3 scripts/measure_cu.py` after
  `npm run e2e`.
- `scripts/measure_cu.py:1` parses recent e2e transactions and compares
  consumed CU to `tests/cu_baselines.json`.
- `docs/CU_BUDGET.md:90` describes the e2e-localnet gate shape.

This is important because the protocol now depends on several high-CU
operations: Poseidon Merkle recomputes, widened schema hashing, and Groth16

### 6. Cryptographic byte-format fixes have regression gates

## What is left

### P0 mainnet blockers

1. SOLID-SEC-048: BabyJubJub prime-order subgroup check does not fit BPF CU

Current status: open with `sec007-skip-onchain` interim bypass.

`register_issuer` still cannot afford the full subgroup check on BPF:
`programs/issuer-registry/src/lib.rs:317`.  The bypass build keeps only the
cheap `is_on_curve` and non-identity gates, with off-chain SDK enforcement as
the load-bearing predicate.  This is acceptable for localnet/devnet bring-up,
but it is not a mainnet control.

Recommended closure: move the subgroup proof into the circuit/trusted-setup
batch, likely alongside SEC-006 Part 2 and SEC-051, or ship a Solana-native
curve syscall if that becomes available.  SDK-only cofactor clearing is not
strong enough by itself because malicious callers can bypass SDKs.

2. SOLID-SEC-012: trusted setup is single-party

The current `circuits/scripts/setup.js` flow is a testnet/single-party setup.
This is a hard mainnet blocker.  The fix is a multi-party ceremony with
transcript verification, artifact hashes, and an on-chain/off-chain manifest
that is treated as part of the release process.

3. SOLID-SEC-006 Part 2: bind `vk_generation` into circuit publics

Part 1 now works operationally.  Part 2 is still deferred because it requires a
circuit revision and trusted-setup cycle.  Without this, the on-chain timelock
is strong operationally, but the public-input contract is not cryptographically
bound to a specific VK generation.

### P1 pre-devnet / external-audit blockers

1. SOLID-SEC-080: schema/global root updates need current-root anchoring

Issuer-tree atomic paths now have the right pre-CPI/current-root anchor.
Schema/global root updates have the new-root Poseidon recompute but do not yet
prove the supplied path is consistent with the current binding root before the
write.  The exact surface is called out in
`sec/SECURITY_REGISTRY.md:160`.

Relevant code:

- `programs/schema-registry/src/lib.rs:429` recomputes `new_root` for
  schema tree updates.
- `programs/schema-registry/src/lib.rs:536` recomputes `new_root` for global
  root updates.
- `apply_schema_tree_root_update` and `apply_global_root_update` enforce
  authority and monotonic slots but do not independently anchor the old path:
  `programs/schema-registry/src/lib.rs:87` and
  `programs/schema-registry/src/lib.rs:167`.

Recommended closure: mirror `verify_issuer_binding_anchor` with
`verify_schema_binding_anchor` and `verify_global_binding_anchor`.

2. SOLID-SEC-081: program-id check does not scan TS literals

`scripts/check_program_ids.py` validates Anchor.toml, `declare_id!`, and
deployment manifests.  It does not yet scan TS code for hand-rolled
`new PublicKey("...")` literals or duplicated program ID constants.  This is a
medium severity CI/governance gap because the verifier SDK hand-rolls
instructions and program IDs are load-bearing.

3. Integration suite is still mostly prose

`tests/integration/README.md` lists scenarios 01..11, but the tree currently
has only `tests/integration/01_registry_init.test.ts`.  The real localnet e2e
happy path is good evidence, but it is not a substitute for negative
behavioral tests:

- replay rejection,
- forged global/schema/issuer binding accounts,
- stale root/path rejection,
- expired credential rejection,
- revocation and cooldown negative verification,
- VK rotation/freeze behavior,
- wrong program IDs / wrong account owners.

This is the biggest remaining evidence gap before an external audit.

4. SOLID-SEC-010: cross-language vectors are incomplete

The current commitment/nullifier vector check passes, but the registry still
marks the larger vector expansion open.  The current gate covers the most
important path but not every primitive that can drift:

- BJJ sign/verify,
- BJJ public key derivation,
- schema hash,
- issuer leaf,
- Poseidon byte/field variants,
- proof public-input packing,
- verifier wire-subset extraction.

5. SOLID-SEC-017: `solid-prover` still uses deterministic test RNG

`tools/solid-prover/src/lib.rs:90` still calls `ark_std::test_rng()`.
The component appears non-production in the current JS/snarkjs path, but that
state is itself risky: dead or half-dead prover code can be wired into mobile
or native flows later.  Either delete/retire `tools/solid-prover` from the
public architecture, or promote it with `OsRng` and a proof-randomness
regression gate.

### P2 / design cleanup

- SOLID-SEC-082: split `cooldown_ends_at` into separate cooldown and dispute
  window fields.  Current status-based reuse is understandable but fragile.
- SOLID-SEC-018: verifier config write lock on every verification caps
  throughput.  The `proof_count` mutation makes every proof contend on the
  singleton verifier config account.
- SOLID-SEC-021: depth-20 global tree caps scale around the current fixed
  depth.  This is not a day-one devnet blocker but matters for product scale.
- SOLID-SEC-013 and SOLID-SEC-043: single-key authority surfaces should move
  behind Squads/DAO threshold before public devnet has meaningful external
  integrations.
- SOLID-SEC-014: shared stake vault should be revisited before meaningful
  stake is at risk.

## Readiness judgment

### Localnet

Status: green enough for internal iteration.

The system has a real e2e reference tx, host Groth16 round-trip coverage, CU
baselines, and a working TS verifier path.  Localnet is no longer blocked on
fundamental "does this execute" questions.

### Devnet

Status: candidate, with warnings.

Devnet deployment is reasonable if it is clearly labeled testnet/experimental
and uses the current `sec007-skip-onchain` build only with telemetry and
operator discipline.  Public developer onboarding should wait until:

- SEC-080 is closed,
- TS program-ID drift scanning is added,
- integration tests cover the most important negative paths,
- docs are reconciled to the current registry.

### Mainnet

Status: not ready.

Mainnet must wait for:

- SEC-048 real fix,
- SEC-012 multi-party trusted setup,
- SEC-006 Part 2 circuit binding,
- multisig/DAO authority controls,
- external audit,
- bug bounty,
- full integration suite and soak tests.

## What I think of the system

The core protocol architecture is strong.  The team has made the right hard
choices: issuer revocation is circuit-visible, nullifiers include issuer-tree
epoch data, verifier roots are owner-checked and reconstructed from accounts,
wire size is handled by a real buffer-account design, and CU is now measured
instead of guessed.

The strongest thing about the project is its security process.  The registry
preserves mistakes instead of hiding them, and the recent fixes show good
debugging discipline: many of the worst bugs only surfaced after earlier
blockers were removed.  That is exactly how deep protocol work tends to feel.

The weakest thing is integration evidence.  There is a lot of proof that
individual invariants work and one strong e2e happy path, but not enough
negative behavioral coverage for the number of trust boundaries.  Before
external users touch it, the project needs fewer prose gates and more tests
that fail loudly when old bugs are reintroduced.

My short version: SolID is now "serious devnet protocol" quality, not "ship
mainnet" quality.  That is a good place to be, but the next phase should be
boring and disciplined: close SEC-080/081/010/017, build the integration
suite, reconcile docs, then do the trusted setup and authority hardening.
