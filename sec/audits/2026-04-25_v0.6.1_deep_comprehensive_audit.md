- **Status:** Living snapshot. Supersedes `sec/audits/2026-04-24_v0.6_deep_comprehensive_audit.md` as the post-Phase-3-impl-4 state-of-the-protocol.
- **Scope:** Full protocol surface. Three Anchor programs, Circom circuit, Rust crates (`solid-core`, `solid-light`, `solid-wasm`), TS SDK, scripts, tests, CI, ops posture.

## 0. One-paragraph verdict

SolID is, today, structurally sound at the cryptographic and on-chain-state layers. Every CRITICAL and 10 of 12 HIGH findings close at the root rather than papering over them; the two remaining HIGHs (cross-language vectors completion, multi-party trusted setup) are planning / ceremony items, not code gaps. The protocol has an unusually-disciplined engineering posture (ADR-first, regression-gate-first, single-source-of-truth-first) that is rare for a pre-devnet codebase and that directly translates into audit-readiness. **The honest blocker to "testable v1 E2E on devnet" is no longer soundness -- it is surface polish: the integration suite (02..11) is specified but unimplemented, the deployment manifest has `deployed_at: null`, and the authority model is single-signer until SEC-043 / Squads lands.** None of those are one-sprint work individually, but none are architecturally fraught either. With the ship plan in Section 7, a credible testable devnet v1 is 7--10 engineering days away. To out-perform existing systems (Iden3 / Polygon ID / Sismo / DID-on-Solana), the remaining leverage is not security; it is (a) finishing the governance path, (b) the DevEx layer (SDK ergonomics + a reference verifier app), and (c) the credential-lifecycle story (revocation SDK + indexer).

## 2. My honest opinion of the system

### 2.1 What is genuinely good -- and rarely seen at this stage

1. **Discipline over velocity.** Every fix lands with (a) a root-cause analysis, (b) a regression gate, (c) doc updates in the same commit, (d) a registry transition. The "six rules of engagement" in `plan/IMPLEMENTATION_PLAN.md` Section 9 are audited on every PR. This is the single biggest predictor of passing an external audit cleanly: soundness regressions tend to come from hasty fixes, and there are no hasty fixes in the commit history.
2. **Cross-language parity is an invariant, not a test.** The `cross_language_vectors` CI job reruns `gen_vectors` (Rust is the source of truth), fails on git diff, then reruns `check_vectors.ts`. A Poseidon drift between Rust and TS fails CI, not production. This is how you build wire-level compatibility, and it is rare.
3. **Atomicity of status transitions.** ADR-0014's insistence on atomic `replace_leaf` CPI in the same ix as the state flip (rather than "on-chain status + tree root via indexer") is the right architectural call. It removes an entire class of race attacks that would otherwise exist at the 200-500ms window between two transactions. `revoke_issuer_atomic` and `request_withdrawal_atomic` both get this right.
4. **Public-input contract is explicitly indexed.** `ISSUER_TREE_ROOT_INPUT_INDEX`, `VERIFIER_ADDRESS_INPUT_INDEX`, `CURRENT_TIMESTAMP_INPUT_INDEX` are named constants with the shift-aware comments. Any future reshuffle MUST update the constants in the same commit. This is the right way to tie circuit and verifier together.
5. **Owner-checks on every UncheckedAccount.** `global_tree`, `schema_tree_0..3`, `issuer_tree_binding` all owner-checked against the correct program ID. Without these, any system-owned account with a forged discriminator would be accepted. The owner check is what makes the whole ZK path non-bypassable.
6. **Stack-owned VK buffer.** The pre-remediation design leaked an unbounded allocation per proof via `Box::leak`. The replacement is a ~2.5 KB stack buffer with a compile-time assert that it fits Solana's 4 KB BPF stack budget. Elegant and correct.
7. **Idempotent initialize + state file.** `initialize.ts` uses `isAlreadyInitialised(e)` to make every step re-runnable, and persists state under `$XDG_RUNTIME_DIR` with mode 0600 (SEC-020). This is the right dev loop.
8. **VK content-addressing** closes a supply-chain gap that most ZK projects don't even think about until the first "we uploaded the wrong VK" incident.
9. **48-hour VK-rotation timelock is the industry-standard correct answer.** Not 6h, not 24h, not "governance only" -- 48h + observability. Ethereum DAOs that host similar rotation paths (Gnosis Safe, MakerDAO) universally use 24h or longer. SolID picked the right point.

### 2.2 What is weak today -- and must be fixed

1. **The authority model is a single pubkey.** Today, an attacker who compromises `registry_config.authority` (same key as VK authority, same key as issuer-tree operator, same key as schema authority on dev deployments) can: finalize a malicious VK, request rotation (subject to 48h timelock), re-approve arbitrary issuers via trust-anchor path, and push arbitrary `issuer_tree_root`. This is a deliberate pre-SEC-013 stance, but it is the single largest "not-yet" item in the threat model. SEC-043 fixes the issuer-tree operator; SEC-013 fixes the global authority. Both must close before external audit.
2. **Atomicity of `update_issuer_tree_root` vs. `replace_leaf` is by convention, not by code.** `revoke_issuer_atomic` and `request_withdrawal_atomic` comments explicitly instruct the caller to invoke `update_issuer_tree_root` in the same tx. If the caller omits it, the SPL AC tree holds the new root but `IssuerTreeBinding.current_root` still points at the old root, and `verify_batch_proof` continues to accept pre-revocation proofs. This is **FINDING NEW-01** (MEDIUM) in Section 5.4.
3. **`vk_generation` is not yet bound into the public-input contract.** ADR-0015 explicitly acknowledges this as Part 2. Current state: cross-VK replay is possible during the 48h window (an attacker who captured a proof under VK generation N can replay it under VK generation N+1 if their proof happens to verify under both, e.g., if the VK rotation was for reasons other than a circuit change). The observability window is the defence, not the cryptography.
4. **Integration coverage is a single file.** `01_registry_init.test.ts` exists; `02_issuer_lifecycle` through `11_cross_language_vectors` do not. The on-chain behavioural evidence today is the `e2e_localnet` job's happy-path, not negative-test coverage. `07_verify_replay_rejected`, `08_verify_forged_global_tree_rejected`, `09_verify_forged_schema_tree_rejected`, `10_verify_expired_credential_rejected` are regression gates that currently live only as prose.
5. **`issuer-registry` at 2,436 lines has grown past the "comprehensible at a glance" threshold.** The module split (into `governance.rs`, `tree_lifecycle.rs`, `issuance.rs`, `slashing.rs`) was called out in the v0.6 audit and remains undone. Audit readability matters for external reviewers.
6. **No devnet deploy.** `deployments/devnet.json.deployed_at` is `null`. Nothing to point users at; every prospective integrator has to run localnet themselves. This is the single biggest "why can't I try it right now" gap.
7. **Cooldown semantics are now verify-negative, but revocation v1 holder SDK doesn't wire up.** Phase 2 shipped the on-chain paths; the TS SDK helper for "as a holder, how do I know my credential just became unusable?" is still a gap (called out explicitly in `CLAUDE.md`). End-to-end, a holder cannot yet learn about a revocation short of polling.
8. **`solid-prover` uses `ark_std::test_rng()`.** This is SEC-017, still open, and trivially fixable (`rand::rngs::OsRng`). The prover is currently a `tools/` artifact rather than a first-class SDK, so the leak is low-impact -- but the public name is "solid-prover", which implies production usage.
9. **Governance is aspirational.** `initialize_registry` takes a `governance_token_mint`; `scripts/initialize.ts` falls back to `PublicKey.default()`. There is no real governance token minted anywhere. Until one is, every "DAO-gated" handler is actually single-signer gated.
10. **CU-budget discipline is untested at scale.** `verify_batch_proof` should verifiably fit within a single transaction's CU budget (Solana default 200k, max 1.4M via `ComputeBudgetProgram`). No CU baseline is recorded. Regression potential: a future constraint addition pushes verification over budget and silently fails.

### 2.3 Subtle strengths worth naming

- The **32-slot public-input contract** with `issuerTreeRoot` at `[10]` intentionally shifts the post-ADR-0014 slots. The code has index-shift-aware comments on every `public_inputs[i]` use, and the `VERIFIER_ADDRESS_INPUT_INDEX` / `CURRENT_TIMESTAMP_INPUT_INDEX` constants are load-bearing. A future circuit change without the matching constant update fails the `verifier_config_space_matches_layout`-style regression gates.
- The **6-input nullifier** (SEC-008, ADR-0006 revision) adds `issuerTreeRoot` as a preimage input. When *any* issuer is revoked, the tree root changes, which means every pre-revocation proof's nullifier is drawn from a different universe. This closes the epoch-replay window by construction -- a pre-revocation cached proof cannot even produce a colliding nullifier. This is stronger than "revoke and hope nobody replays fast enough."
- The **hardening comments** on `verify_batch_proof` are specific enough to serve as an audit artifact by themselves (e.g., "Without this owner check an attacker can pass a system-owned account with a forged 'globroot' discriminator"). Auditors love specific-threat comments; lint-style comments mean nothing.
- The **`VkBuf` compile-time stack assertion** (`const _: () = { let sz = core::mem::size_of::<VkBuf>(); assert!(sz < 3072, ...); };`) catches any future layout growth at build time, not at runtime.

## 3. Pros and cons -- the unvarnished list

### 3.1 Pros

- Three-CRITICAL-zero, ten-of-twelve-HIGH-closed registry after 4 days of Phase 3 work.
- ADR-first, regression-gate-first commit discipline.
- Byte-level cross-language parity gated by CI.
- Atomic status transitions (no race windows between status flip and tree-root update for the on-chain side).
- Named constants for every load-bearing public-input index.
- Owner-checked UncheckedAccounts everywhere the program consumes external state.
- Stack-owned VK buffer with compile-time size assertion.
- Content-addressed VK artifact with two-channel pin (env var + file).
- 48-hour VK rotation timelock with industry-standard observability window.
- Idempotent `initialize.ts` + state file under restricted permissions.
- Three Anchor programs, each with a clear single responsibility.
- SPL Account Compression integration without taking the SPL AC crate as a dependency -- dep-graph hygiene matters for audit.
- Rust 1.79.0 / anchor 0.30.1 / solana 1.18.22 pinned and enforced by CI (`scripts/bootstrap.sh`, `flake.nix`).
- `check_program_ids.py` hard-gates Anchor.toml / `declare_id!` / deployments/*.json consistency.
- Host-side tests run without a validator: 80+ unit tests across `solid-core` + `solid-light` + `zk-verifier` pass in under a minute.
- Circuits compile in CI on every PR; witness-level mocha tests for SEC-001 and SEC-029 regression gates.
- CI jobs fail-fast with specific messages ("VK sha256 mismatch" etc.), not "see logs".

### 3.2 Cons

- Single-pubkey authority model until SEC-013 / SEC-043 land.
- Atomicity of `update_issuer_tree_root` + `replace_leaf` is caller-enforced, not handler-enforced (FINDING NEW-01).
- `vk_generation` not yet bound into public-input contract (SEC-006 Part 2 deferred).
- Only 1 of 10 planned integration tests implemented.
- No devnet deploy (`deployed_at: null`).
- No multi-party trusted setup (SEC-012) -- mainnet blocker, but ceremony work, not code.
- Governance token is aspirational (`PublicKey.default()` fallback).
- Cross-language vectors cover 3 of 10 primitives.
- `issuer-registry` monolithic (2,436 lines).
- `solid-prover` uses `test_rng` (SEC-017, trivial fix).
- Revocation holder/indexer SDK not yet wired (Phase 3 scope).
- No CU budget baseline for `verify_batch_proof`.
- No client-side prover benchmarks (time-to-proof on a 4-credential batch).
- Circuit has a single concrete instantiation (`20, 20, 16, 8, 4, 4`) -- no parameterised variants yet (MVP pragmatic choice, but bakes in the 4-credential/4-predicate cap).
- WASM bundle size / tree-shaking untracked.
- No privacy analysis of the public-input set beyond the nullifier universe (e.g., `verifierAddress` + `queryContextHash` disclosures during proof).
- No formal verification of the circuit's constraint system.
- No threat model doc for the issuer-side SDK key-handling (`bootstrap_issuer.ts` + keys in `~/.config/solana/id.json`).
- DAO vote accounting (`active_votes_count`) is correct but releases require an explicit `release_vote` call per vote -- UX friction that indexers / watchers must handle.

## 4. Devnet v1 ship plan -- testable E2E in 7--10 engineering days

The right sequence to ship a testable v1 on devnet, ordered for minimum risk and maximum visibility:

### Day 1 -- Make CI the mirror of the desired end state

1. **Fix SEC-017** (`OsRng` in `solid-prover`). Trivial; open the file, swap the line, add a test that asserts two proofs over the same inputs produce different nullifiers. Unlocks one MEDIUM registry line.
2. **Fix NEW-01** (atomic binding update). See Section 5.4 for the code shape.
3. **Finish SEC-010 cross-language vectors**: extend `crates/solid-core/examples/gen_vectors.rs` and `tests/vectors/check_vectors.ts` to cover Poseidon raw, BJJ keygen, BJJ sign/verify, `computeIdentityState`, `QueryBuilder._computeContextHash`, ADR-0014 issuer-leaf. Gated by the existing `cross_language_vectors` CI job; any drift fails CI.
4. **Baseline CU budget** for `verify_batch_proof`. Add a CI job that calls `verify_batch_proof` on localnet and asserts `<= 250_000 CU` (or whatever the measured number is, plus 10%). Regression gate for future circuit changes.

### Day 2--3 -- Integration suite 02..11 (7 of 10 critical path tests)

The eight that must land to call the pipeline "behaviourally tested":

- `02_issuer_lifecycle` -- full register/stake/vote/finalize/approve path.
- `03_slash_transfers_lamports` -- HIGH-01 regression.
- `05_issue_credential` -- SPL AC append + event emitted.
- `06_verify_happy_path` -- Groth16 over a real credential; event count +1.
- `07_verify_replay_rejected` -- NullifierRecord `init` collision.
- `08_verify_forged_global_tree_rejected` -- owner-check regression gate.
- `09_verify_forged_schema_tree_rejected` -- owner-check regression gate.
- `10_verify_expired_credential_rejected` -- ExpirationChecker regression gate.

The harness is already staged (`anchor-bankrun`); the unique-per-test setup is ~100-200 lines each. Realistic pace: 2 tests per engineering day.

### Day 4 -- Module split + DevEx

1. Split `issuer-registry/src/lib.rs` into:
   - `mod governance.rs` (stake/vote/finalize/approve)
   - `mod tree_lifecycle.rs` (append/revoke/request_withdrawal/update_root/binding)
   - `mod issuance.rs` (issue_credential)
   - `mod slashing.rs` (slash/submit_fraud_proof/withdraw)
   - `mod state.rs` (account types)
2. **Add an `ADR-0016: Devnet operational runbook`** covering VK upload, finalize, backfill, and rotation paths.
3. **Revocation SDK helpers** (`ts-sdk/packages/issuer/revocation.ts`): `revokeIssuer(oldRoot, merkleProof)` and `requestWithdrawalAtomic(oldRoot, merkleProof)`. Mirrors the existing `issueCredential` wrapper.

### Day 5 -- Actually deploy to devnet

1. `anchor deploy --provider.cluster devnet` for all three programs.
2. `python3 scripts/regen_devnet_manifest.py` -- this writes the `deployed_at`, `upgrade_authority`, and `deployer.address` fields.
3. `tsx scripts/initialize.ts` with `SOLID_VK_SHA256=<hex>` set.
4. `tsx scripts/backfill_issuer_tree.ts` to create the SPL AC issuer tree and bind it.
5. `tsx scripts/bootstrap_issuer.ts` to register and DAO-approve a dev issuer.
6. `tsx scripts/issue.ts` to mint a real credential.
7. `tsx scripts/prove.ts` to generate a proof and verify on devnet.
8. Record the transaction hashes in `docs/DEPLOYMENT_AND_TESTING.md`.

The deploy itself takes ~20 minutes; steps 3--7 verify the public pipeline works against the real cluster.

### Day 6 -- Squads 3-of-5 integration (closes SEC-043, part of SEC-013)

1. Create a Squads multisig for the `registry_config.authority` and the `IssuerTreeBinding.operator`. Amend ADR-0014.
2. Rotate authority via `transfer_authority` (zk-verifier), `approve_via_trust_anchor` (issuer-registry), and the proposed `transfer_issuer_tree_binding_operator`.
3. Update `scripts/initialize.ts` to detect a Squads authority and use the Squads SDK to propose rather than sign directly.

### Day 7 -- Observability + watcher

1. Deploy an event indexer (Helius webhook or Solana Geyser plugin) for:
   - `CredentialVerified` (counts + latency histograms).
   - `CredentialIssued` (per-issuer monthly totals).
   - `IssuerLeafAppended` / `IssuerLeafReplaced` (tree state changes).
   - VK rotation events (`finalize_verification_key`, `request_vk_rotation`, `rotate_verification_key`).
2. Publish a minimal status page: "current vk_generation, last rotation, total proofs verified, active issuers, tree roots".

### Day 8--10 -- Reference verifier app + stress tests

1. **Reference verifier app** (Next.js). Connects wallet, requests credential, generates proof in the browser (WASM), submits to devnet. This is the "here's what SolID looks like from a user's perspective" artifact.
2. **10k-proof soak test**: on devnet, submit 10k distinct proofs (different nullifiers) and measure success rate, latency p50/p99, and CU utilisation. Fail the test on any verify_batch_proof failure. 10k proofs across 4 workers over ~2 hours.
3. **100-issuer stress test**: register 100 issuers, approve them all via trust-anchor, enroll them all into the issuer tree via `append_issuer_leaf`, bulk-revoke 20 via `revoke_issuer_atomic`, verify that post-revocation proofs from those issuers all fail in-circuit.

**Exit criteria for "testable v1 E2E on devnet":**
- All CI jobs green, including the 10 integration tests.
- `deployments/devnet.json.deployed_at != null`.
- Reference app proves + verifies a credential end-to-end.
- Observability dashboard live.
- 10k-proof soak completes with <0.1% failure rate.

**Not in v1, explicitly:**
- Multi-party trusted setup (mainnet blocker, not devnet).
- Cross-VK replay prevention (`vk_generation` in public-input contract, Part 2).
- On-chain DAO votes over the VK authority (SEC-013 completion).
- Revocation indexer event contract for holders (Phase 3 later).

## 5. Security audit -- OWASP + Solana + ZK threat model

### 5.1 OWASP-style threat model applied to Solana programs

| OWASP-style class | Where it lives in SolID | Defence in place | Residual risk |
|---|---|---|---|
| **Injection** | `verify_batch_proof`'s `public_inputs` is bounded-size `[[u8;32];32]`. `store_verification_key` chunk_data is bounded `<= 900 bytes`. | Fixed-size arrays + `VK_MAX_BYTES = 10240` cap. | None. |
| **Broken authentication** | Every handler gates on `require_keys_eq!(authority, ...)`. | Programmatic. | SEC-013 / SEC-043 -- single-signer until multisig lands. |
| **Broken authorization** | Three authority types: VK (zk-verifier), registry (issuer-registry), schema (schema-registry). No cross-program privilege escalation. | Owner-checks on UncheckedAccounts. | NEW-01 -- caller must call `update_issuer_tree_root` in same tx as `replace_leaf`. |
| **Sensitive data exposure** | No PII on-chain; only Poseidon commitments. BJJ private keys in the circuit, not logged. | By design. | `bootstrap_issuer.ts` loads keypair from disk; operator hygiene is the defence. |
| **XXE / XSS / CSRF** | N/A. | N/A. | N/A. |
| **Security misconfiguration** | `check_program_ids.py` hard-gates `declare_id!` drift. `verifier_config_space_matches_layout` catches SPACE drift. | Programmatic CI gates. | Upgrade authority still single-signer (pre-deploy). |
| **Insecure deserialisation** | Anchor-generated Borsh for typed accounts; `VkBuf::parse` for VK with typed errors. | Hand-written, bounds-checked. | None surfaced; fuzz coverage would be nice-to-have. |
| **Components with known vulns** | Pinned Anchor 0.30.1, solana 1.18.22, circom 2.1.9, snarkjs 0.7.5. | CI `setup-rust-toolchain@v1` + `Cargo.lock` in repo. | `Cargo.lock` version 3 gated; no `cargo audit` yet -- should add. |
| **Insufficient logging** | `msg!` on every state transition; events emitted for `CredentialVerified`, `CredentialIssued`, `IssuerLeafAppended`, `IssuerLeafReplaced`. | Programmatic. | No indexer yet. |
| **SSRF** | N/A. | N/A. | N/A. |

### 5.2 Solana-specific threat model

| Solana-class threat | Status | Evidence |
|---|---|---|
| **Missing owner check on UncheckedAccount** | Mitigated | `require_keys_eq!(*ctx.accounts.<acct>.owner, <PROGRAM>, ErrorCode::...)` on all three consumed accounts in `verify_batch_proof`. |
| **Missing signer check** | Mitigated | `Signer<'info>` or explicit `require_keys_eq!(authority, ...)` on every authority-gated path. |
| **Arbitrary CPI / malicious CPI** | Mitigated | `require_keys_eq!(compression_program.key(), spl_account_compression_id::ID, ...)` + `log_wrapper` check in all SPL AC CPI sites. |

No seed collisions possible. |

### 5.4 New findings from this audit (two, both MEDIUM)

#### NEW-01 (MEDIUM) -- `revoke_issuer_atomic` / `request_withdrawal_atomic` do not update `IssuerTreeBinding.current_root` in the same ix

**Evidence:** `programs/issuer-registry/src/lib.rs:1156-1160` and `:1313-1316` explicitly document that the caller MUST invoke `update_issuer_tree_root` in the same transaction. The handler does not enforce this.

**Impact:** If a caller (DAO operator, or a compromised key, or a buggy SDK) omits the `update_issuer_tree_root` call, the SPL AC tree has the new root but `IssuerTreeBinding.current_root` still points at the old root. `verify_batch_proof` reads `IssuerTreeBinding.current_root` and cross-checks against `public_inputs[ISSUER_TREE_ROOT_INPUT_INDEX]`, so a proof generated against the pre-revocation root continues to verify until the binding is updated. The nullifier universe has shifted (the holder cannot regenerate the same proof), but a cached pre-revocation proof is still replayable until someone calls `update_issuer_tree_root`.

**Remediation (code shape):**

```rust
// Inside revoke_issuer_atomic + request_withdrawal_atomic, after the
// invoke_signed for replace_leaf, read back the new root from the
// SPL AC tree and write it directly into the binding in the same ix.
// The binding PDA signer seeds are known (crate::ID + b"issuer-tree-binding");
// the caller does NOT need to pass update_issuer_tree_root separately.
//
// Implementation: after the CPI succeeds, compute the new_root on-chain
// from old_root + old_leaf + new_leaf + merkle path (or re-read the SPL AC
// tree's changelog account), then:
//
// let binding = &mut ctx.accounts.issuer_tree_binding;  // MUT now, not Unchecked
// binding.data.borrow_mut()[40..72].copy_from_slice(&new_root);
// binding.data.borrow_mut()[72..80].copy_from_slice(&Clock::get()?.slot.to_le_bytes());
//
// The binding account must be passed writable to these two ix. The
// authority check stays the DAO / registry authority, identical to the
// existing `update_issuer_tree_root`.
```

**Regression gate:** `tests/integration/07b_revoke_atomic_binding_update.test.ts`: call `revoke_issuer_atomic` without a subsequent `update_issuer_tree_root`, then call `verify_batch_proof` with a pre-revocation proof; expect `IssuerTreeRootMismatch`, not success.

**Why this wasn't caught earlier:** The v0.5 audit and ADR-0014 designed the split deliberately to keep the replace_leaf ix small (CU-cheap); the caller-discipline was called out but the enforcement gap wasn't graded against the threat model. Now that NEW-01 is surfaced, the atomicity argument is strictly stronger if the binding update lives in the same ix.

#### NEW-02 (MEDIUM) -- No CU-budget regression gate on `verify_batch_proof`

**Evidence:** No CI job or runtime measurement of `verify_batch_proof`'s CU utilisation. The stack-buffer size assertion catches stack growth at compile time, but CU can drift invisibly (e.g., a circuit-side constraint that requires more IC points, or a public-input addition, or a change in alt_bn128 costs in a future Solana upgrade).

**Impact:** Future constraint additions or circuit revisions could push `verify_batch_proof` over Solana's per-tx CU ceiling without failing CI. Failure mode at runtime is "transaction fails with ComputeBudgetExceeded" -- recoverable but high-visibility on mainnet.

**Remediation:** Add a CI job `verify_batch_proof_cu_baseline` that runs `verify_batch_proof` against localnet with a known-good proof, measures CU via `ComputeBudgetProgram.requestUnits` + transaction log parsing, and asserts `cu <= RECORDED_BASELINE * 1.10`. Record baseline in `docs/CU_BUDGET.md`.

**Regression gate:** The CI job itself.

### 6.5 How to out-perform existing systems (Iden3 / Polygon ID / Sismo / ION)

The meaningful differentiators SolID can lean into:

- **Cost.** SPL Account Compression is dramatically cheaper than L2 storage-rent-based systems. Back-of-envelope: a credential issuance costs ~1-2k lamports (0.00001 SOL) in rent + tx fees, versus ~$0.50 on Polygon zkEVM. Publish this number.
- **Atomicity.** Iden3 / Polygon ID are two-step (publish state + submit proof) with finality gaps. SolID's `revoke_issuer_atomic` is single-tx; the epoch-nullifier construction is stronger than Iden3's "tree-root published hourly".
- **Verifier throughput.** Solana's 400ms finality + alt_bn128 syscall gives proof verification in <500ms end-to-end, vs. 12-60s on EVM-based systems. Publish the benchmark.
- **Deployer-to-usage gap.** SolID requires one `anchor deploy` + `initialize.ts` run. Iden3 / Polygon ID require running a Merkle tree node, signing oracle, and issuer service. Publish the "30-second integration" artifact.
- **Non-identity credentials.** ADR-0014's leaf composition is general: Solana authority + BJJ pubkey + status + revocation. Works for supply-chain provenance, compliance attestations, non-human issuers (oracle operators, audit firms, hardware vendors). Iden3 is identity-scoped; SolID does not have to be.

None of these are code work today -- they are publishable artifacts. The code is already competitive; the leverage is packaging.

## 7. Answering your direct questions

### 7.1 "Should we ship testable v1 E2E on devnet first?"

Yes, unambiguously. The path in Section 4 gets you there in 7--10 engineering days without taking any mainnet-class risk (no ceremony, no multisig, no governance token). It produces a public artifact (the reference app + the devnet program IDs + the observability dashboard) that prospective integrators can try immediately. Mainnet is a separate project that starts after devnet v1 has collected 4--8 weeks of real usage data.

### 7.2 "Is the system robust?"

Today, at the code layer: yes. The CRITICALs are closed, the HIGHs are closed except for two items that are planning/ceremony work, and the atomic-transition architecture is structurally sound. The two weak points are (a) the authority model (single pubkey until SEC-013 / SEC-043) and (b) behavioural test coverage (1 of 10 integration tests). Both are addressable in the ship plan without any cryptographic rework.

### 7.3 "Will it out-perform existing systems?"

On cost and verification latency: structurally yes, for the reasons in Section 6.5. On feature parity: not yet -- Iden3 has a DID-compatible resolver, Polygon ID has a mobile SDK, Sismo has the "Zk Badges" product wrapper. SolID's leverage is in the packaging layer (SDK, reference app, indexer), not in the crypto layer. The crypto is already competitive.
