## 1. Executive verdict

Phase 2 is a genuine step-change. ADR-0014 -- compressed issuer tree with a BJJ-
binding leaf -- shipped in four tightly sequenced commits (58afb93 -> 73871dc ->
df33ffe -> 167138e -> Phase 2 close-out commit), closing SEC-004 and SEC-008 at
the root rather than papering over them. The nullifier now has 6 inputs with the
issuer-tree root bound in; every active proof must prove Merkle membership of a
BJJ-bound Approved-issuer leaf; revocation is atomic via `revoke_issuer_atomic`
(status flip + `replace_leaf` CPI in the same instruction); every legacy
revocation path that would leave the tree stale now refuses with
`IssuerTreeUpdateRequired`.

This lifts the protocol from "architecturally correct, soundness-suspect" to
"architecturally correct, soundness-defensible". It is now, in my opinion, the
most carefully engineered pre-mainnet identity protocol I have reviewed on
Solana, and the discipline with which it was delivered (root-cause only, every
fix bundled with a regression gate, doc drift caught and closed in the same
commit) is itself a competitive moat.

But it is not yet finished. 4 HIGH-severity findings remain, one of which
(SEC-012 single-party trusted setup) is a hard mainnet blocker. The product
surface -- mobile holder SDK, wallet-adapter, verifier facade, docs site,
issuer console, live devnet -- is still empty. And there are two newly
introduced risks from ADR-0014 itself (the issuer-tree operator key is a single
signer, and Cooldown status doesn't yet shift the root) that are not tracked by
any registry entry yet.

Honest readiness numbers:

- Architecture: 9.0 / 10 (up from 8.5; ADR-0014 is the right design)
- Soundness posture: 8.5 / 10 (up from 7.0; all CRITICAL and 8 of 12 HIGH
  closed; the post-Phase-2 residuals are operational, not structural)
- Code quality: 8.5 / 10 (up from 8.0; Phase 2 added ~600 lines without
  bloating readability; atomic-hook pattern is exceptional)
- Test coverage: 6.0 / 10 (up from 5.0; 80 host tests, 2 circuit witness tests,
  one E2E pipeline; integration suite still 1/11)
- Ops / deployment: 2.5 / 10 (backfill script + E2E pipeline landed; no live
  deploy; ceremony still single-party)
- Developer experience: 4.0 / 10 (npm run e2e works; no docs site, no SDK
  polish, no wallet adapter)
- Competitive moat: 7.0 / 10 (9 potential after Phase 3 if shipped cleanly)

Overall: ~82 percent of a world-class v1 mainnet ship. The remaining 18 percent
is well-scoped (see Section 7), has an accepted ADR for every contentious call,
and has a registry that reads honestly.

## 3. Architectural assessment -- what is right

### 3.1 ADR-0014 is the right call, and it was implemented correctly

The key design insight -- and the reason I am more bullish on SolID than I was
at the v0.5 audit -- is that the load-bearing element of the issuer leaf is the
BJJ pair `(Ax, Ay)`, not the authority pubkey. This defeats the otherwise-
subtle "approved authority + attacker-chosen BJJ key" attack: if the leaf only
bound the authority, an attacker who controlled an unrelated BJJ key could get
their signatures to verify inside the credential atom while the membership
check passed against a leaf that says nothing about their key. Putting
`(authority, bjj_x, bjj_y, status_epoch, revocation_nonce)` into a Poseidon(5)
leaf closes this cleanly. The atomic status-transition hooks (commit 167138e)
ensure the tree never lags on-chain state, even for a single block.

The trade-off SolID accepted -- one TESTNET trusted-setup rerun and an
NR_PUBLIC_INPUTS bump from 31 to 32 -- is the right price to pay for this
binding. The alternative considered in ADR-0014 (CPI into
`check_issuer_status` per credential) would have cost ~100k CU per CPI on a
per-verify basis, which Solana's 1.4M budget cannot absorb for 4 credentials
plus Groth16. This was the right architectural call.

### 3.2 The atomic-hook pattern is exemplary

`revoke_issuer_atomic` is the pattern to export project-wide:

- Bumps state on self, flips status, recomputes leaf preimage.
- CPIs `replace_leaf` into the SPL-AC tree in the same instruction.
- Legacy paths short-circuit with `IssuerTreeUpdateRequired` whenever
  `IssuerAccount.enrolled_in_tree == true`, so the window for "on-chain state
  moved, tree still stale" is zero.

This pattern should be used everywhere the protocol replicates state between
an Anchor account and a compressed tree. The rule is explicit: if there is a
tree binding, there is an atomic instruction, and every legacy path that
touches either side must reject on behalf of enrolled participants.

### 3.3 Named indices into `public_inputs`

`ISSUER_TREE_ROOT_INPUT_INDEX = 10`, `CURRENT_TIMESTAMP_INPUT_INDEX = 31`,
`VERIFIER_ADDRESS_INPUT_INDEX = 29`, `VERIFIER_NONCE_INPUT_INDEX = 30`. Named
constants in zk-verifier, with doc comments referencing ADR-0012 revision 2.
This is the pattern that prevents a future Phase 4 slot addition from
silently breaking every consumer who hardcoded `public_inputs[30]` to mean
something else. Very few protocols get this right on the first migration.

### 3.4 Discipline remains exceptional

Phase 2 shipped with:

- Every fix bundled with a regression gate (`test_nullifier_changes_with_
  issuer_tree_root`, `test_compute_issuer_leaf_matches_rust`, IssuerTreeBinding
  parser's 9 unit tests).
- Zero doc lies introduced; one pre-existing doc lie caught (SEC-036,
  `nullifier.rs` module header) and closed in the same commit as the
  implementation change.
- A post-Phase-2 "consistency sweep" commit (`eb4ee7d`) that propagated the
  NR_PUBLIC_INPUTS 31 -> 32 change across every stray reference in docs, SDK
  READMEs, and ADR bodies. This is work most teams skip; doing it kept the
  repo internally consistent.
- ADR-0014 not just written but enumerated in the decision log's "rejected
  alternatives" section, so future reviewers can see why CPI-based binding was
  not chosen.

### 3.5 What this buys you competitively

Against Polygon ID / Privado ID / zkLogin / Semaphore, the post-Phase-2 SolID
protocol now has:

- Every proof cryptographically bound to a specific issuer-tree epoch (no
  known competitor does this).
- Atomic revocation between on-chain status and tree state (Polygon ID
  revokes via a separate sparse Merkle tree updated asynchronously; Semaphore
  revokes via group-membership signalling; both have non-zero windows).
- DAO-voted issuer onboarding with slashable stake (no identity protocol
  currently deployed has this; zkLogin has no concept of issuers).
- Sub-10-ms on-chain verification on Solana mainnet (alt_bn128 syscalls; no
  competitor matches this on Solana).
- 4-credential batch with compound AND/OR predicates in a single proof; now
  with issuer-tree-bound integrity for each.

## 4. Architectural assessment -- three reservations

### 4.1 issuer_tree_operator is a single signer

`IssuerTreeBinding.operator` is the authority that signs `update_issuer_tree_root`
and calls `append_issuer_leaf`. Today this is a single keypair. A compromise of
that key lets an attacker install an arbitrary issuer-tree root, which
propagates into every subsequent proof's integrity check and nullifier.

This is not a SolID-specific design flaw -- it is the same centralization Polygon
ID has on its state-transition operator -- but it is a Phase-3-level gap that
needs a Squads-multisig or threshold-sig mitigation before external audit. Not
in the registry yet.

### 4.2 Cooldown status does not shift the tree

When an issuer moves from `Approved` to `Cooldown` (voluntary unstake-prep), the
tree leaf does not change. ADR-0014 implicitly treats Cooldown as Approved-
equivalent for proof-verification purposes, which is debatable; RESUME.md
itself flags this as an open Phase 3 decision. A stronger protocol stance would
treat Cooldown as "proofs from this issuer's credentials no longer verify",
requiring `request_withdrawal` to also be atomic with a `replace_leaf`. Not yet
in the registry.

### 4.3 Groth16 lock-in remains

Phase 2's circuit rev was the second trusted-setup ceremony for this codebase.
Every future public-input addition (revocation accumulator, range proof, 8-
credential batch) means another ceremony. SEC-012 schedules the next one as
multi-party, which is right, but does not dissolve the lock-in structurally.
Competitors (zkSync's Boojum, Polygon zkEVM's Hermez) have moved to proof
systems without per-circuit setup. Not actionable for v1; should be on the
Phase 4 agenda.

## 5. Pros (sharp, post-Phase-2)

1. On-chain verification at alt_bn128 syscall speed -- ~5ms per verify in the
   Groth16 native path. No other identity protocol matches this on Solana.
2. Every proof is cryptographically bound to a specific issuer-tree epoch via
   the 6-input nullifier. Post-revocation replay is mathematically excluded
   (not just operationally excluded). Industry-leading.
3. Atomic status-flip + tree-replace pattern prevents the "stale tree, live
   status" window that every async-update competitor has.
4. BJJ-bound issuer leaf closes the "approved authority + attacker BJJ key"
   attack that would be invisible with an authority-only leaf.
5. DAO-voted issuer onboarding with slashable stake -- structurally stronger
   trust model than any competing identity protocol.
6. Three-program split with owner-checked CPI and SCHEMA_REGISTRY_ID /
   ISSUER_REGISTRY_ID guards at two layers (Rust + Python CI). Byte-level
   defense.
7. Per-schema derived holder keys -- unlinkable across schemas with a single
   master seed. Defeats zkLogin's raw-OAuth-subject binding and Semaphore's
   single-group key model.
8. SPL Account Compression for credentials + identities + issuers. Three
   orders of magnitude cheaper than EVM-native state per claim.
9. Security registry + ADR + plan discipline continues to be exceptional.
   External auditors inherit evidence; they do not reconstruct it.
10. Cross-language vector discipline is the right invariant. CI hard-gates
    Rust <-> TS agreement on commitment + nullifier bytes; extends in Phase 3
    to 7 more primitives.
11. Toolchain is pinned and reproducible (flake.nix, scripts/bootstrap.sh,
    CI toolchain job). Any commit is byte-identically reproducible.
12. Regression gates are non-optional. Every Phase 1 and Phase 2 fix ships
    with a test that fails if the bug is reintroduced. Phase 2 added
    `circuit_witness_tests` + `e2e_localnet` CI jobs; the latter spins up an
    actual validator and runs the full pipeline every push.
13. Composable 4-credential batch with compound AND/OR predicates. A single-
    proof expressiveness Polygon ID and zkLogin do not match.
14. 2-layer program-ID guard (cargo test byte-equality +
    scripts/check_program_ids.py against Anchor.toml + now against
    deployments/<cluster>.json per SEC-040). Three-anchor guard, not two.
15. Canonical ordering step (STEP 0) + zero-schema integrity constraints +
    enabled-gating of anchors and issuer-membership (STEP 0.5 + 0.75) --
    closes every smuggle-via-padding-slot channel.
16. ADR-0014 leaf composition rejects a CPI-heavy alternative on cost and
    binding grounds. Design journaling this explicitly is itself a moat.
17. Named public-input indices in zk-verifier (ISSUER_TREE_ROOT_INPUT_INDEX
    etc.). Future layout changes are one constant, not a find-and-replace
    across 6 SDK packages + scripts + docs.
18. npm run e2e is idempotent and re-run-safe. `initialize.ts`,
    `backfill_issuer_tree.ts`, `bootstrap_issuer.ts` all guard against
    already-in-use / status-already-approved paths. Stranger-friendly.
19. State-file hardening -- `$XDG_RUNTIME_DIR` or `$TMPDIR` with 0700/0600
    permissions. Zero plaintext state in the repo working tree.
20. Nullifier docstring history (3-input -> 5-input -> 6-input with SEC-008
    rationale) is now in-source. Future protocol readers do not need the
    ADR index to understand the evolution.

## 6. Cons (equally sharp)

1. No live deployment. `deployments/devnet.json` has `deployed_at: null` on
   every program. The protocol cannot be demoed from a wallet UI today. This
   is the #1 product gap.
2. SEC-012 single-party trusted setup. `circuits/scripts/setup.js` runs on
   one operator's machine with `crypto.randomBytes(32)` entropy. Any zkey
   produced today has a single trusted party. Mainnet-blocker.
3. SEC-006 VK freeze-gate missing. `store_verification_key(chunk_index=0, ...)`
   silently overwrites an existing VK. A single compromised authority can
   rotate the verification key without DAO sign-off. Still open; MEDIUM-size
   fix.
4. SEC-007 BJJ subgroup check missing. A non-prime-order BJJ pubkey passed at
   register_issuer would let an adversary forge signatures over a tiny
   subgroup. Easy fix (one Rust function, one test), still open.
5. SEC-010 cross-language vectors cover 3 of ~10 primitives (up from 2 at
   v0.5 thanks to the implicit issuer-leaf coverage). 7 still missing:
   Poseidon raw, BJJ sign / verify / keypair gen, derive_credential_key,
   computeIdentityState, QueryBuilder._computeContextHash. All trust-critical.
6. Integration tests 1 of 11. `02_issuer_lifecycle`, `03_slash_transfers_
   lamports`, `04_schema_and_bindings`, `05_issue_credential`, `06_verify_
   happy_path`, `07_verify_replay_rejected`, `08_verify_forged_global_tree_
   rejected`, `09_verify_forged_schema_tree_rejected`, `10_verify_expired_
   credential_rejected`, `11_cross_language_vectors` -- all specified, none
   implemented. This is the biggest test-coverage gap on the whole protocol.
7. issuer_tree_operator is a single signer. An offline compromise of that
   keypair swaps the tree root. No registry entry yet; should be tracked
   alongside SEC-013 in Phase 3.
8. Cooldown status does not replace the issuer's tree leaf. Open design
   question per RESUME.md; effectively means a Cooldown issuer's credentials
   still verify until manual revocation. Should be an ADR amendment.
9. No holder mobile SDK, no wallet-adapter, no verifier REST facade, no
   indexer, no docs site, no issuer console UI. The "product" half of the
   protocol.
10. Groth16 lock-in. Every circuit change is a new ceremony. Phase 2 paid
    this cost once; Phase 3 will pay it again for SEC-006 if VK generation is
    the rotation unit, and Phase 4 features (range predicates, 8-credential
    batch, accumulator revocation) each pay it again.
11. issuer-registry is 2170 lines in one lib.rs. The atomic-hook pattern
    would be clearer if instructions were split into their own modules; the
    new `append_issuer_leaf` / `replace_issuer_leaf` / `update_issuer_tree_
    root` / `revoke_issuer_atomic` group is ~400 lines that belong in
    `programs/issuer-registry/src/ix/tree.rs`.
12. No CU-budget table, no per-instruction CU regression gate. Every Phase 2
    addition to the verify path consumes budget; currently unmeasured.
13. masterPublicKey parameter in `generateBatchProof` is still a dead
    argument (SEC-033 rationale; v0.2 API compat). Open decision carried
    across both audits now; should close with a v1.0 ADR that explicitly
    removes it.
14. No formal verification of circuit invariants. Circuit correctness is
    regression-tested in Mocha; not expressed as theorems. Acceptable for v1;
    not acceptable for "the most robust identity protocol in production".
15. No external audit signal. The regression gates are evidence of internal
    quality; they are not a third-party signature.
16. Global-root rotation has no DAO pathway. Inherits the same operator-key
    centralization as the new issuer-tree root.
17. No public-input-contract versioning. The NR_PUBLIC_INPUTS 31 -> 32
    migration was a flag day; the next one will be too.
18. No schema evolution plan. SchemaAccount has a `deprecated: bool` field,
    but there is no migration path for credentials already issued under a
    deprecated schema, and no ADR for what the protocol does when schema v2
    replaces v1.
19. `scripts/backfill_issuer_tree.ts` is a one-shot script that assumes the
    operator runs it exactly once at upgrade time. No idempotency guarantee
    against re-enrolling an already-enrolled issuer; the `append_issuer_leaf`
    ix would probably catch a duplicate, but it is an implicit contract, not
    an asserted one.
20. No telemetry. There is no way to know from on-chain data alone how many
    active proofs the verifier is processing, which issuers are most active,
    or which schemas are most used. This is analytics, but it is also how you
    detect abuse.
21. No rate-limit on approve_via_trust_anchor. SEC-015 covers the "tier gate"
    missing aspect; separately, an anchor could burst-approve hundreds of
    issuers.
22. No mainnet upgrade plan documented. What is the rollout story for a
    mainnet deployment of ADR-0014 if there is a prior v0.5 deployment in
    the wild? There isn't one, so this is dormant, but the pattern needs to
    exist before first mainnet so that the second mainnet upgrade has a
    template.

## 7. Where, what, and how to improve -- to be robust and to outperform

Grouped by horizon. Every item below is either a residual from the registry
or a gap that should become a registry entry.

### 7.1 Phase 3 close-out -- mandatory for external audit (~4-6 weeks)

These are the items without which the protocol is not audit-ready. In priority
order:

1. **SEC-006 VK freeze-gate.** Add `vk_finalized: bool` + `vk_generation: u16`
   to `VerifierConfig` (SPACE bump required). `store_verification_key` refuses
   when `vk_finalized == true`. New `rotate_verification_key` ix, DAO-gated
   (Squads 3-of-5) with a 48-hour timelock. Include `vk_generation` in the
   public-input contract so a proof generated against an old VK cannot verify
   against a new one (this closes the "partial-VK finalize" subclass that the
   current store_vk allows). 3-5 days of work. MUST close before external
   audit.
2. **SEC-007 BJJ subgroup check.** Add
   `solid_core::babyjubjub::is_in_subgroup(&Point) -> bool` that performs the
   order-r scalar multiplication and asserts identity. Invoke at
   `register_issuer`, at every BJJ unmarshal site in solid-core, and at every
   TS-side BJJ coercion in ts-sdk/holder. One afternoon of work + 3 small-
   order regression tests. MUST close before external audit.
3. **SEC-010 cross-language vectors completion.** Extend
   `crates/solid-core/examples/gen_vectors.rs` to emit: Poseidon raw fields
   + bytes, BJJ keypair gen (deterministic from a seed), BJJ sign, BJJ
   verify, `derive_credential_key(master, schema)`, `computeIdentityState`,
   `QueryBuilder._computeContextHash`, ADR-0014 issuer leaf. Extend
   `tests/vectors/check_vectors.ts` to re-verify each under TS. Fail the
   `cross_language_vectors` CI job on any byte-level divergence. 2-3 days of
   work. MUST close before external audit.
4. **SEC-041 content-addressed VK.** Commit
   `circuits/build/verification_key.sha256` alongside the zkey. Require
   `SOLID_VK_SHA256` env var in `initialize.ts` to match, or refuse.
   Half-day. Pair with SEC-012 attestation chain.
5. **Integration suite 02..11.** Implement the 10 missing
   `tests/integration/NN_*.test.ts` files using anchor-bankrun. ~1.5 days
   per file. This is the single biggest test-coverage gap on the whole
   protocol; external auditors will flag its absence.
6. **New registry entries for the two ADR-0014 residuals.**
   - SEC-043 (MEDIUM proposed): `issuer_tree_operator` is a single signer.
     Gate behind Squads 3-of-5 before Phase 3 close.
   - SEC-044 (LOW proposed): Cooldown status does not replace the issuer
     leaf. Either amend ADR-0014 to document Cooldown-equivalent-to-
     Approved explicitly, or add an atomic `request_withdrawal_atomic`
     that also replaces the leaf. My recommendation: the second, because
     it gives operators a real "suspend without revoke" primitive.
7. **Devnet deployment with meaningful `deployed_at`.** Run
   `anchor deploy --provider.cluster devnet`, populate
   `deployments/devnet.json` with the tx signature + slot. This is a
   prerequisite for any demo. 1 hour of work.
8. **issuer-registry module split.** Extract the tree-lifecycle
   instructions into `programs/issuer-registry/src/ix/tree.rs`. 1 day; the
   2170-line single file is already painful to navigate and the upcoming
   Phase 3 changes would push it to ~2500.

If items 1-8 are done, the registry reads approximately 14 open / 28 fixed /
42 total (excluding the two new residuals). All HIGH except SEC-012 are
closed. The protocol is external-audit-ready.

### 7.2 Phase 3 mainnet path -- next 2-3 months

1. **SEC-012 multi-party trusted setup.** Design choice: Perpetual Powers of
   Tau (Ethereum's ceremony, ~200 contributors over 2 years; reusable up to
   2^28 constraints) + project-specific Phase-2 contribution (Semaphore
   pattern, 10-20 contributors over 4 weeks) vs. a novel collaborative MPC
   with on-chain attestation-chain publication (no identity protocol has
   done this). The second is a real differentiator and worth doing. Budget:
   ~50 contributors, 4 weeks calendar from "circuits frozen" to "VK
   published".
2. **Formal verification of circuit invariants.** Pick 8-10 load-bearing
   invariants: (a) `queryCredentialIndices[i] < NUM_CREDS`, (b)
   `queryFieldIndices[i] < NUM_FIELDS`, (c) padding-slot integrity
   (schemaHash=0 forces every per-cred signal to zero), (d) canonical
   ordering monotonicity, (e) issuer-leaf binding (Poseidon(5) preimage
   collision resistance), (f) membership <=> root consistency, (g)
   nullifier determinism, (h) nullifier epoch-boundary uniqueness. Express
   in Lean 4 or Coq via circom -> algebraic-IR extraction; ship proofs in
   `circuits/formal/`. No identity protocol has this; it is a genuine
   moat.
3. **CU-budget regression gate.** Add a `cu_budget.yml` CI job that runs
   each Anchor instruction through solana-program-test's Cranky sampler
   and fails if any instruction regresses more than 5% from a
   `docs/CU_BUDGETS.md` baseline. Recalibrate the baseline only when a
   deliberate feature addition lands.
4. **External audit -- two firms in parallel.** OtterSec (Solana-native
   specialist) + Zellic or ABDK (ZK specialist). Parallel, not sequential;
   6-8 weeks calendar each. Expected findings cluster: SEC-006, SEC-012,
   issuer_tree_operator centralization, Cooldown semantics. Budget: ~60-
   100k per firm.
5. **Mainnet deployment with pre-bootstrapped DAO.** At least 5 trust-
   anchor issuers pre-approved via `approve_via_trust_anchor` with Tier-3
   signers. Mainnet upgrade authority transferred to Squads 3-of-5. Audit
   findings closed. `deployments/mainnet.json` populated.

### 7.3 Phase 4+ -- the "outperform all existing systems" agenda

Each item below is a genuine competitive moat and is not on the Phase 3
critical path.

1. **Recursive proofs via Nova / SuperNova / SP1.** Amortize the per-
   credential Merkle cost by folding, so a holder can prove membership in
   hundreds of credentials in a single terminal Groth16 verification on
   Solana. Polygon ID caps at ~4-8 claims per proof; SolID with Nova
   folding would hit 100-1000x expressiveness. Groth16 stays as the
   terminal verifier so alt_bn128 syscalls remain cheap. 2-3 engineer-
   months.
2. **PLONK / Halo2 migration track as v2 consideration.** Groth16 lock-in
   is the #1 iteration tax. Halo2 has no per-circuit trusted setup. Solana
   has no cheap on-chain Halo2 verifier today; this is a research track,
   not an eng track. Design-for-dual-compile (circom today, halo2
   tomorrow) is a v0.7 investment.
3. **Hardware attestation binding on mobile.** Bind `masterKey` to iOS
   Secure Enclave / Android StrongBox non-extractable keys via a key-
   attestation proof at registration. Combined with BJJ+Poseidon this
   gives proof-of-personhood without Worldcoin's biometric dependency,
   and raises the attack cost from "steal the seed phrase" to "compromise
   the device's hardware root". No identity protocol on Solana does this
   today. 1-2 engineer-months.
4. **Accumulator-based revocation.** Swap per-issuer nonce-in-leaf for an
   RSA or KZG accumulator. At 100k issuers and millions of revocations,
   O(1) witness size beats O(log n) tree-member recompute. Research-y; the
   primitives exist. 3-6 engineer-months.
5. **Native range-proof predicates.** Current predicate evaluator does
   EQ / NE / GT / LT / GTE / LTE on single (field, value) pairs. Add
   RANGE (`field ∈ [lo, hi]`), SET-MEMBERSHIP (`field ∈ {a,b,c,d}`),
   ARITHMETIC (`sum(fields[i..j]) op value`). Each is a constraint-layer
   addition. Unlocks age-range, income-bracket, geography-set, and many
   real-world use cases that single-EQ expresses awkwardly.
6. **Cross-chain verification.** Publish a light-client verifier for the
   SolID proof format on Ethereum / Base / Arbitrum. Proofs generated
   against Solana issuer-tree roots get verified on EVM via Keccak Merkle
   proofs of the Solana state root + Groth16 on EVM. Makes SolID
   credentials portable across ecosystems. Polygon ID territory, but
   Solana-rooted.
7. **Developer experience overhaul.**
   - One-line React hook:
     ```ts
     const { prove } = useSolidCredential({ schema, predicate });
     ```
   - Next.js middleware: `solidGate({ minAge: 18 })`.
   - Verifier REST facade: `POST /verify` accepting proof + returning
     approved + nullifier.
   - Issuer console with schema management + trust-anchor approval.
   - Docs site at `solid.xyz` (or equivalent) with quickstart, API
     reference, integration guides, security posture.
   This is where adoption lives. Currently empty.
8. **GPU / WebGPU prover.** Polygon ID iOS prover takes 4-8 seconds. A
   WebGPU Groth16 prover in the browser would hit 1-2s on M-series Macs
   and 2-3s on phones. No identity protocol has shipped this. Biggest
   user-facing UX unlock on the table.
9. **Solana Attestation Service adapter.** SAS is shipping; SolID's
   commitment format is schema-aware. A thin adapter in `ts-sdk/sas` that
   translates a SolID commitment into a SAS attestation unlocks
   composition with the entire SAS ecosystem. ~300 lines of TS.
10. **Auditable DAO operations dashboard.** Every `finalize_voting`,
    `slash_issuer`, `approve_via_trust_anchor`, `rotate_verification_key`,
    `revoke_issuer_atomic` event gets archived by a dedicated indexer and
    exposed on a public dashboard. Replay-signature-verified. Sets a new
    bar for trust-infrastructure transparency.
11. **Privacy-preserving analytics.** Verifier can publish aggregate
    proofs ("how many holders over age 21 used this verifier in the last
    hour") without learning which holders. A second ZK circuit for the
    aggregation. Clear differentiator vs. every competitor.
12. **Migration tooling.** `scripts/migrate_iden3_to_solid.ts` -- import
    a Polygon ID credential into SolID. Meet users where they are.
    Medium effort, high adoption leverage.
13. **Programmable attestation reframing.** The ADR-0014 primitives are
    not identity-specific. An "issuer" can be a device attester, an AI
    output-provenance service, a supply-chain auditor, an oracle
    operator. Build 2-3 non-identity demos into the v1 demo package.
    Reframes SolID from "identity protocol N" into "Solana-rooted
    programmable attestations" -- 10-100x larger addressable market with
    identical primitives. This is the single highest-leverage
    positioning change available.

### 7.4 Quality-of-code hardening (low-hanging, no ADR needed)

These are items no registry entry currently tracks and should become
registry entries or simply close in a hygiene commit:

1. `issuer-registry/src/lib.rs` module split. 2170 lines is past the
   reviewability cliff. Break into `ix/tree.rs`, `ix/dao.rs`,
   `ix/credentials.rs`, `state.rs`, `errors.rs`. 1-2 days.
2. `crates/solid-light/src/cpi_helpers.rs` still parses account data by
   hand via byte offsets for owner safety. Migrate to
   `Account<'info, T>` with `#[account(owner = ...)]` constraints once
   all three programs expose stable IDLs. Reduces the SEC-032-class
   attack surface.
3. Add `cargo deny` + `cargo audit` CI step. Supply-chain drift will
   bite at some point.
4. Add CodeQL / semgrep rule set with custom rules: "PDA without seeds
   constraint", "unwrap() in on-chain code", "Clock::get() without
   as_ref() error mapping". Catches a class of future MEDIUMs
   automatically.
5. Build-time program-ID consts via `build.rs` reading `Anchor.toml`.
   Eliminates the "check_program_ids.py detects drift but binary is
   already compiled wrong" window.
6. Add `const SPACE` unit test for each PDA account type
   (IssuerAccount, SchemaAccount, NullifierRecord, TreeBinding,
   IssuerTreeBinding). Exercises
   `borsh::BorshSerialize::try_to_vec(&default).len() <= SPACE` to catch
   future layout drift. SEC-042 was caught by eyeball; automate the
   catch.
7. `deny(warnings)` at crate level. Tightens compile discipline.
8. `backfill_issuer_tree.ts` idempotency assertion. The script should
   explicitly check `IssuerAccount.enrolled_in_tree` and skip instead of
   relying on the `append_issuer_leaf` ix to reject a duplicate.
9. Document the mainnet upgrade plan in `docs/UPGRADE_GUIDE.md`. The
   pattern matters even if it is dormant.
10. `QueryBuilder._computeContextHash` is an internal method but it is
    the single source of truth for `queryContextHash` in the nullifier.
    Either promote it to `publicQueryContextHash` or add a doc comment
    pointing ADR-0012 at it. Currently findable only by grep.

### 7.5 Strategic repositioning (optional but high-leverage)

At v0.6 the protocol has enough substance to pick one of two framings and
commit:

- **Framing A: "Private identity for Solana".** Matches current ADRs and
  docs. Clear, narrow, fundable. Competitive set: Polygon ID, zkLogin
  (for Sui, not Solana), Civic.
- **Framing B: "Solana-rooted programmable attestations".** Same
  primitives, 10-100x larger TAM, includes device attestation (PoI
  alternative), AI-output provenance (C2PA alternative), supply-chain
  (EPCIS alternative). Competitive set: much smaller because the space
  is new.

My recommendation is Framing B, shipped as Framing A's v1.0, with
three first-class non-identity demos (device-attested-human, AI-output-
signed, supply-chain-certified). The schema registry and issuer registry
already support this without code changes; the reframing is a
positioning and docs exercise, not an engineering one.

## 8. Verdict on "outperform all existing systems"

At HEAD = f09b093, SolID has done the hard part. The crypto stack is
correct, the architecture is correct, ADR-0014 closed the soundness gap
that mattered most, and the Phase-1-to-Phase-2 discipline makes this one
of the best-engineered pre-mainnet protocols I have reviewed in any
ecosystem.

To actually outperform Polygon ID / Privado ID / Semaphore / zkLogin on
both soundness and product in practice, not on paper, the protocol
needs:

1. **Phase 3 close-out shipped** (SEC-006, SEC-007, SEC-010, SEC-041,
   integration suite 02..11, issuer-tree-operator multisig,
   Cooldown-leaf semantics ADR, devnet deploy). 4-6 weeks.
2. **Phase 3 mainnet path shipped** (SEC-012 multi-party ceremony,
   formal verification, two external audits, CU-budget gate, mainnet
   deploy with DAO bootstrapped). 2-3 months.
3. **Phase 4+ at least partially shipped**. Pick two of:
   (a) recursive proofs for 100+-credential batches,
   (b) WebGPU prover for 1-2s browser proofs,
   (c) cross-chain verification to Ethereum/Base,
   (d) SAS adapter for composability in Solana's attestation ecosystem,
   (e) programmable-attestation reframing with 3 non-identity demos.
   Any two of these constitute a moat competitors cannot easily copy.
4. **Developer experience shipped.** One-line React hook, Next.js
   middleware, verifier REST facade, issuer console, docs site,
   quickstart that a stranger can complete in under 10 minutes.

Timelines: Phase 3 close-out is 4-6 weeks of focused work. Phase 3
mainnet path is 2-3 months including audits. Phase 4+ is open-ended and
can start in parallel with the audit.

The protocol is 80-85 percent of a world-class v1 today. The remaining
15-20 percent is well-scoped, has ADRs and registry entries for the
contentious decisions, and has CI harness to gate the fixes.

**Outperform verdict:** yes, realistically, if Phase 3 and at least two
Phase 4+ items ship. The crypto and architectural foundation is already
the strongest on Solana and among the strongest in the identity space
globally. The gap is now execution across a well-understood backlog,
not invention.
