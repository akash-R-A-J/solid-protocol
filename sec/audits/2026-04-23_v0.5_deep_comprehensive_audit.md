# SolID Protocol -- v0.5 Deep Comprehensive Audit

Date: 2026-04-23
Commit: 4fba821 (Phase 2 CI harness + ADR-0014 landed on top of Phase 1 close-out)
Scope: Full-system audit covering architecture, current state, security posture,
pros, cons, and a prescriptive roadmap to "out-perform all existing systems".

Dense, honest, forward-looking. No varnish.

---

## 1. Executive verdict

SolID is a serious, unusually disciplined attempt at Solana-native private
credentials. The crypto choices are correct, the governance thinking is ahead of
most competitors, and the security registry / ADR / plan discipline is arguably
best-in-class for a pre-mainnet protocol.

But it is not yet competitive with Polygon ID / Privado ID on operational
maturity, and it has 6 HIGH-severity soundness / liveness gaps still open. The
architecture is sound; the execution is 70-75 percent done against what a v1
mainnet ship needs.

- Current phase: Phase 1 CLOSED. Phase 2 kick-off IN PROGRESS (ADR-0014
  accepted, CI harness landed, implementation pending).
- Registry state: 25 open / 17 fixed / 42 total. CRITICAL 0 open, HIGH 6 open,
  MEDIUM 9, LOW 6, INFO 4.
- Honest readiness rating:
  - Architecture: 8.5 / 10
  - Code quality: 8 / 10
  - Security posture: 7 / 10 (improving fast)
  - Test coverage: 5 / 10 (host tests strong, integration weak)
  - Ops / deployment: 2 / 10 (no live deployment, ceremony single-party)
  - Developer experience: 4 / 10 (no docs site, no wallet adapter, no dashboard)
  - Competitive moat: potentially 9 / 10 if Phase 2-4 ships; 5 / 10 as of today.

## 3. Architectural assessment -- what is right

### 3.1 Program split is correct

The three-program factoring (zk-verifier, issuer-registry, schema-registry) is
textbook clean. Each has a single responsibility; cross-program wiring is done
through owner-checked PDAs, not via shared state. That is exactly the pattern
Anchor + Solana make easy to get wrong, and here it is right.

The ownership check model (cpi_helpers::verify_schema_tree_binding_for_issue,
SCHEMA_REGISTRY_ID constant with SEC-032 two-layer guard at both cargo test and
check_program_ids.py) is arguably tighter than anything in the Anchor ecosystem
I am aware of.

### 3.2 The crypto choices are coherent

- Groth16 on alt_bn128 via Solana syscalls -- the one on-chain ZK verification
  path that is actually cheap on Solana today. (ADR-0001.)
- BabyJubJub + Poseidon for signatures -- matches the circomlib stack;
  cross-chain portable to every Ethereum-adjacent system. (ADR-0002.)
- SPL Account Compression for credential + identity + (soon) issuer trees --
  cheap issuance at scale. (ADR-0003, ADR-0014.)
- Per-schema derived credential keys Poseidon(masterKey, schemaHash) -- limits
  linkability across schemas while keeping a single master seed. (ADR-0005.)
- 5-input hardened nullifier already landed. 6-input epoch-bound variant
  designed in ADR-0014. This is more careful than the 2-input Poseidon(sk,
  schema) pattern still used by most research code.
- Identity anchor with enabled gate so padding slots skip the global-tree
  inclusion check -- this is the kind of subtle correctness detail most teams
  ship a broken version of.

### 3.3 Governance is ahead of the field

DAO-voted issuer registration (register_issuer + vote_on_issuer +
finalize_voting), stake + slash, trust-anchor bypass for bootstrap, cooldown +
withdrawal request, fraud-proof submission. ADR-0009 explains the bypass
carefully. Most identity protocols have no on-chain governance for issuers --
they either hard-code a root of trust (zkLogin), require off-chain DID docs
(Iden3), or outsource to a centralized admin. SolID's on-chain DAO is a
structural moat.

### 3.4 Discipline is the real asset

plan/IMPLEMENTATION_PLAN.md Section 0 (non-negotiables), root-cause-only
Section 2, one-source-of-truth rule, and the living SECURITY_REGISTRY with
commit-hash pointers are exceptional. I have reviewed a lot of protocol
codebases; very few maintain this level of record-keeping. When external
auditors look at this repo, they will not be starting from scratch -- they will
be auditing evidence already laid out.

### 3.5 What this lets you claim that Polygon ID / zkLogin / Semaphore cannot

- Solana-native on-chain verification (Polygon ID requires EVM / zkEVM).
- 4-credential batch with compound AND/OR predicates in a single proof (most
  competitors verify one claim at a time; Iden3 v2 supports a small merged
  proof, but the batch-of-4 + compound-logic pattern is distinctive).
- On-chain DAO issuer governance (zkLogin and Polygon ID have none).
- SPL-AC-compressed issuance cost (Polygon ID issues on L2 state with per-claim
  cost).
- Hardened 5-input nullifier with pending epoch binding (more conservative than
  Semaphore's 2-input hash(sk, externalNullifier)).

## 4. Architectural assessment -- two reservations

### 4.1 Groth16 lock-in

Every new constraint in the batch circuit forces a new trusted-setup ceremony.
ADR-0014 is honest about this: SEC-004 + SEC-008 fix together is a single
rerun, but any future feature (new predicate, revocation accumulator, range
proof) is another ceremony. Over a multi-year horizon this is a severe tax.
Competitors moving to PLONK / Halo2 / Plonky2 / SP1 pay no such tax. The
decision to stay on Groth16 is correct for v1 alt_bn128 Solana performance but
should be re-evaluated at v2. See Section 7.

### 4.2 Circuit monolith

batch_credential_query.circom does canonical ordering, identity binding,
credential atoms, expiration, predicate evaluation, AND/OR, query context
hashing, and nullifier derivation in one template. It is readable, but adding
the issuer-tree membership proofs for SEC-004 will push it past the comfortable
monolith threshold. The ADR-0014 design adds 64 private inputs and 4
subcircuits; at some point a factor into multiple proofs + recursive
aggregation is healthier. Again: Section 7.

## 5. Pros (sharp list)

1. Solana-native on-chain verification at ~5ms using alt_bn128 syscalls. No
   competitor matches this on Solana.
2. On-chain DAO issuer governance with slashing -- structurally stronger trust
   model than any competing identity protocol.
3. Three-program split with owner-checked CPI -- clean separation, every
   boundary enforced.
4. Hardened nullifier (5-input) already landed; 6-input design accepted --
   moves replay protection past the typical 2-input state of the art.
5. Per-schema derived holder keys -- unlinkable across schemas with a single
   master seed. Beats zkLogin's raw OAuth binding.
6. SPL Account Compression for credentials + identities + (soon) issuers --
   three orders of magnitude cheaper than EVM-native storage per claim.
7. Security registry + ADR + plan discipline is exceptional -- every change is
   traceable to a root cause, a commit, and a regression gate. External
   auditors will find this repo easy to work in.
8. Cross-language vector discipline is the right invariant -- CI hard-gates
   Rust <-> TS agreement on commitment + nullifier bytes. This catches a whole
   class of bugs that normally reach prod.
9. Toolchain is pinned and reproducible (flake.nix, scripts/bootstrap.sh, CI
   toolchain job). You can check out at any commit and get a byte-identical
   build. Rare.
10. Regression gates are non-optional -- every Phase 1 fix ships with a test
    that fails if the bug is reintroduced. Phase 2's new circuit_witness_tests
    job extends this to the circuit layer.
11. Composable 4-credential batch with compound AND/OR predicates -- a
    single-proof expressiveness no deployed identity protocol currently
    matches.
12. Two-layer program-ID guard (cargo test byte equality +
    scripts/check_program_ids.py against Anchor.toml) -- stronger than any
    other Anchor program I have seen.
13. Canonical ordering step in the batch circuit (STEP 0.5) forces integrity
    of zero-slots -- prevents a whole class of "smuggle a non-zero via a
    zero-schema slot" attacks.

## 6. Cons (equally sharp list)

1. No live deployment. deployments/devnet.json has deployed_at: null and
   upgrade_authority: null for all three programs. You cannot demo without
   running a localnet. That is a serious go-to-market gap in 2026.
2. SEC-004 is the biggest open soundness hole. The circuit trusts private-input
   issuer pubkeys; nothing pins them to IssuerAccount. Revoked issuers' proofs
   still verify. External auditors will flag this as CRITICAL unless ADR-0014
   is implemented before audit.
3. SEC-007 BJJ subgroup check missing. A malformed pubkey of non-prime-order
   subgroup passed at issuer registration would let a malicious prover forge
   signatures that verify over a tiny subgroup. Easy fix, still open.
4. SEC-012 single-party trusted setup. Any v1 zkey produced today has a single
   trusted party. Competitors (Semaphore, Polygon ID) did community ceremonies
   in 2022. Not mainnet-shippable as-is.
5. Integration test coverage is 1 of 11 -- only 01_registry_init.test.ts is
   implemented. 02_voting, 03_slashing, 04_schema, 05_tree, 06_verify,
   07_replay, 08_batch, 09_revocation, 10_tree_authority, 11_large_batch are
   specified but empty.
6. Cross-language vectors cover 2 of 10 primitives (SEC-010). CI catches
   commitment + nullifier drift; does not catch Poseidon raw, BJJ sign/verify,
   derive_credential_key, computeIdentityState,
   QueryBuilder._computeContextHash. All five are trust-critical.
7. Revocation v1 workflow not wired through the SDK. The circuit and on-chain
   support are in place, but a holder cannot actually perform a revocation
   today.
8. VK freeze-gate missing (SEC-006). store_verification_key(chunk_index=0, ...)
   silently overwrites an existing VK. Single pwned authority can rotate the
   verification key without DAO sign-off. MEDIUM-effort fix still open.
9. No holder mobile SDK, no wallet-adapter hook, no verifier facade. The full
   "product" layer on top of the protocol is empty. Developer-integration
   friction is very high right now: currently the integration path is
   `ts-node scripts/prove.ts`.
10. Groth16 lock-in on the circuit. Any feature addition requires a new
    trusted-setup ceremony. Competitors moving to PLONK / Halo2 will eventually
    eat this as a cost-of-iteration advantage.
11. issuer-registry is 1583 lines in one lib.rs file. Not a bug, but
    approaching the point where a module split would improve reviewability.
    The upcoming ADR-0014 implementation will add ~300 lines of issuer-tree
    plumbing; that is when it becomes necessary.
12. No CU-budget table and no per-instruction CU regression gate. Solana's
    1.4M cap is real. The Groth16 verify consumes a large fraction; adding CPI
    into check_issuer_status per credential could push the verify instruction
    over. Phase 1 dodged this via ADR-0014 (choosing the tree path), but the
    risk recurs with every feature.
13. masterPublicKey parameter in generateBatchProof is a dead argument -- the
    SEC-033 fix made it redundant; the carry was kept for v0.2 API compat.
    Open decision in RESUME.md.
14. Legacy scripts/e2e_state.json path is undocumented in operator runbooks --
    the new helper writes under $XDG_RUNTIME_DIR / $TMPDIR, but anyone with a
    stale runbook will hit this.
15. Top-of-file comment in crates/solid-core/src/nullifier.rs still documents
    the old 3-input Poseidon(holderPrivateKey, schemaHash, verifierNonce)
    formula. Implementation is the 5-input hardened version. Actual doc lie
    in-source, not caught by any registry entry. See Section 7.4.
16. No formal-verification pipeline. Circuit invariants like
    queryCredentialIndices[i] < NUM_CREDS are enforced by constraints and
    regression-tested by circuit_witness_tests. They are not expressed as
    theorems anywhere. This is fine for v1; not fine for "outperform all
    existing systems".
17. No external audit completed on the post-Phase-1 code. The regression gates
    are evidence of your own quality; they are not a third-party signal.
18. Global-root rotation has no DAO pathway. update_global_root is gated by an
    authority; the issuer tree in ADR-0014 will inherit the same pattern. A
    rogue authority compromising the root is a one-sig incident.
19. No public-input-contract versioning. NR_PUBLIC_INPUTS = 31 -> 32 when
    ADR-0014 lands; there is no mechanism for old-proof + new-circuit mixed
    verification during the transition. Deploy day will be a flag day.
20. Scripts rely on $XDG_RUNTIME_DIR / $TMPDIR state files -- fine in CI,
    weird UX for a dev running locally who sees state "disappear" on reboot.

## 7. Where, what, and how to improve -- to robust and to outperform

This is the section that asks the strategic question: how does SolID beat
Polygon ID, zkLogin, Semaphore, Privado ID on both soundness and product?
Grouped by horizon.

### 7.1 Phase 2 must-do (next 2-4 weeks, to land a clean v0.6)

These are already in plan/RESUME.md "Next action". Treat as the hard path:

1. Implement ADR-0014 -- compressed issuer tree. 6 surfaces: circuit (add 64
   private inputs + 4 membership sub-circuits + public input at index [10]),
   zk-verifier (bump NR_PUBLIC_INPUTS to 32, add issuer_tree_binding account
   owner-checked against ISSUER_REGISTRY_ID), issuer-registry (append /
   replace_leaf on every status transition, add revocation_nonce: u64 to
   IssuerAccount), solid-light (new verify_issuer_tree_binding helper
   mirroring the schema variant), ts-sdk/issuer and ts-sdk/holder (fetch
   issuer Merkle path at proof time), and scripts/backfill_issuer_tree.ts
   (one-shot migration). Closes SEC-004 and SEC-008.
2. SEC-006 VK freeze-gate -- add vk_finalized: bool to VerifierConfig, gate
   store_verification_key on it, add a new rotate_verification_key instruction
   behind a DAO-voted 48-hour timelock.
3. SEC-007 BJJ subgroup check -- one Rust function
   babyjubjub::is_in_subgroup(&Point) -> bool that does order-r scalar
   multiplication, assert == identity. Call at register_issuer and every BJJ
   unmarshal site.
4. SEC-010 cross-language vectors -- extend
   crates/solid-core/examples/gen_vectors.rs to emit Poseidon raw hashes, BJJ
   sign/verify signatures, derive_credential_key outputs, computeIdentityState
   commitments, QueryBuilder._computeContextHash digests. Extend
   tests/vectors/check_vectors.ts to re-verify them under TS. Fail CI on any
   byte-level divergence.
5. Integration suite -- implement 02_voting.test.ts through
   11_large_batch.test.ts using anchor-bankrun. 10 scenarios, roughly 1-2 days
   each. These are what /tests/integration/README.md already specifies.
6. Revocation v1 end-to-end -- holder SDK revokeCredential(nonce), issuer SDK
   rotateIssuerTreeLeaf(authority), indexer event contract. Wire the existing
   on-chain support through.
7. Deploy to devnet (not just build). Populate deployments/devnet.json.
   Publish the three program IDs with concrete deployed_at.

If Phase 2 ships with 1-7 done, the registry becomes approximately
8 open / 34 fixed / 42 total, all CRITICAL/HIGH closed except SEC-012, and
the protocol is external-audit-ready.

### 7.2 Phase 3 -- external audit + mainnet (next 2-3 months)

1. Multi-party trusted-setup ceremony (SEC-012). Design choice: traditional
   Perpetual-Powers-of-Tau + phase-2 circuit contribution (Semaphore pattern)
   vs. novel collaborative MPC with on-chain zk-audit logs publishing
   contribution transcripts. The second is a differentiator worth
   considering -- no identity protocol has done this. Budget: ~50
   contributors, 4 weeks from "freeze circuits" to "publish VK".
2. Formal verification of circuit invariants. Pick 5-10 load-bearing
   invariants (range checks, anchor-enabled gating, padding-slot integrity,
   nullifier determinism, canonical-ordering monotonicity). Express in lean4
   or coq. Ship the proofs in circuits/formal/. Publish as part of the audit
   packet. This is a competitive moat -- no identity protocol has it.
3. CU-budget regression gate. Add a CI job that measures compute units for
   each instruction via solana-program-test + Cranky and fails if any
   instruction regresses more than 5 percent. Publish the baseline in
   docs/CU_BUDGETS.md.
4. External audit by two firms. OtterSec (Solana specialist) + Zellic or
   ABDK (ZK specialist). Run them in parallel, not sequentially. Budget: 6-8
   weeks calendar, ~60-100k per firm for this scope.
5. Mainnet deployment with the DAO already bootstrapped -- at least 5
   trust-anchor issuers pre-approved, mainnet upgrade authority transferred
   to a 3-of-5 multisig, audit findings closed.

### 7.3 Phase 4+ -- where to "out-perform all existing systems"

This is the strategic layer. Each item below is a genuine competitive moat.

1. Recursive proofs via Nova / SuperNova / SP1 -- amortize the per-credential
   Merkle cost by folding, so a holder can prove membership in hundreds or
   thousands of credentials in a single on-chain verification. Polygon ID
   caps out around 4-8 claims per proof; this would give SolID a 100-1000x
   expressiveness advantage. Requires a second proof system alongside
   Groth16, but Groth16 stays as the terminal verifier so alt_bn128 syscalls
   remain cheap.
2. PLONK / Halo2 migration track as a v2 consideration. Groth16 lock-in is
   the #1 tax on iteration. Halo2 has no per-circuit trusted setup. Solana
   does not yet have a cheap on-chain Halo2 verifier, so the migration is
   not free -- but designing the circuit in a way that can be dual-compiled
   to Groth16 (today) and Halo2 (future) is a v0.7 investment that pays back
   forever.
3. Hardware attestation binding on mobile. Bind the holder's masterKey to
   iOS Secure Enclave / Android StrongBox non-extractable keys via a
   key-attestation proof at registration. Combined with BJJ / Poseidon this
   gives proof-of-personhood without Worldcoin's biometric dependency, and
   raises the attack cost from "steal the seed phrase" to "compromise the
   device's hardware root". No identity protocol on Solana does this today.
4. Revocation via accumulator (RSA or KZG) instead of per-issuer nonce. At
   100k+ issuers, a tree update per revocation is still O(log n) on-chain
   but becomes awkward off-chain to re-prove membership. A vector commitment
   with constant-size witnesses would be genuinely better at scale.
   Research-y, but the primitives exist.
5. Range-proof predicates. Current predicate evaluator supports EQ / NE /
   GT / LT / GTE / LTE with single field + single value. Add native range
   predicates (fieldValue ∈ [lo, hi]), set-membership predicates
   (fieldValue ∈ {a, b, c, d}), and arithmetic predicates
   (sum(fields[i..j]) <op> value). Each is a constraint-layer addition.
   This unlocks real-world use cases (age-range, income-bracket,
   geography-set) that single-EQ cannot express cleanly.
6. Cross-chain verification. Publish a light-client verifier for the SolID
   proof format on Ethereum / Base / Solana L2s. Proofs generated against
   Solana roots get verified on EVM via Keccak-based Merkle proofs of the
   Solana state root + Groth16 check. Makes SolID credentials portable
   across ecosystems. This is the Polygon ID territory, but Solana-rooted.
7. Developer experience overhaul. One-line React hook:
   const { prove } = useSolidCredential({ schema, predicate }). Next.js
   middleware: solidGate({ minAge: 18 }). Verifier REST facade: POST /verify
   accepting a proof + returning approved / nullifier. Issuer console with
   schema management + trust-anchor approval UI. This is the half of the
   protocol that is currently empty, and it is where adoption lives.
8. GPU / WebGPU prover. Polygon ID's iOS prover takes 4-8s. A WebGPU Groth16
   prover in the browser would hit 1-2s on M-series Macs and 2-3s on phones.
   There is published research; nobody has shipped one for an identity
   protocol yet. Biggest UX unlock imaginable.
9. Solana Attestation Service adapter. SAS is shipping; SolID's commitment
   format is already schema-aware. A thin adapter in ts-sdk/sas that
   translates a SolID commitment into a SAS attestation unlocks composition
   with the entire SAS ecosystem. ~300 LoC of TS.
10. Auditable DAO operations. Every finalize_voting, slash_issuer,
    approve_via_trust_anchor, rotate_verification_key event emits a
    structured log that a dedicated indexer archives. Publish a public DAO
    dashboard showing every governance action ever taken, with replay-sig
    verification. Sets a new bar for transparency.
11. Privacy-preserving analytics. Verifier can publish aggregate proofs
    ("how many holders over age 21 used this verifier in the last hour")
    without learning which holders. Uses a second ZK circuit for the
    aggregation. A clear product-layer differentiator vs. Polygon ID (which
    does not address aggregate analytics at all).
12. Migration tooling. scripts/migrate_iden3_to_solid.ts: import a Polygon
    ID credential into SolID. Meets users where they already are. Medium
    effort, high adoption leverage.

### 7.4 Quality-of-code hardening (low-hanging but load-bearing)

Things noticed reading the tree that no registry entry currently tracks:

1. crates/solid-core/src/nullifier.rs:3-4 documents the old 3-input
   nullifier formula. The implementation is the 5-input hardened version.
   This is a doc lie in source. Open a LOW-severity registry entry and fix
   in the Phase 2 prelude style.
2. issuer-registry/src/lib.rs is 1583 lines in one file. Split into
   instructions/ + state/ + events/ modules. Not a rush, but before
   ADR-0014 adds its ~300 lines the split is cheaper.
3. cpi_helpers.rs parses account data by hand via byte offsets for
   owner-check safety. Works, but brittle. Consider migrating to
   anchor-lang's Account<'info, T> with #[account(owner = ISSUER_REGISTRY_ID)]
   once all three programs are Anchor and the IDL ABI is stable. Reduces
   the SEC-032-class attack surface.
4. No cargo deny or cargo audit CI step. Supply-chain drift will bite at
   some point.
5. No CodeQL / semgrep rule set. Custom rules for "PDA without seeds
   constraint", "unwrap() in on-chain code", "Clock::get() without as_ref()
   error mapping" would catch a lot of future MEDIUMs automatically.
6. Two-layer program-ID guard is great for three programs; does not
   generalize. Build crates/solid-light/build.rs that reads Anchor.toml at
   build time and emits the IDs as consts. Eliminates the risk that
   scripts/check_program_ids.py detects drift but the binary is already
   compiled wrong.
7. The VerifierConfig::SPACE comment in source was already caught once
   (SEC-042). There are similar space-literal + field-layout couplings in
   IssuerAccount, SchemaAccount, NullifierRecord, TreeBinding. Add a
   const SPACE unit test for each that exercises
   borsh::BorshSerialize::try_to_vec(&default).len() <= SPACE to catch
   future layout drift.
8. No deny(warnings) at crate level. Helpful when onboarding new
   contributors -- compile discipline stays tight.

### 7.5 One strategic pivot to consider

The biggest single lever is this: SolID is currently framed as "private
identity for Solana". The ADR-0014 compressed-issuer-tree design unlocks a
reframing: "Solana-rooted programmable attestations" -- not just human
identity, but any attestation (device attestation, AI-output provenance,
supply-chain claims, oracle signatures, off-chain compute receipts). The
primitives are the same; the addressable market is 10-100x larger. The schema
registry already supports arbitrary schemas; the issuer registry already
supports non-human issuers (oracle operators, audit firms, hardware vendors).
Committing to this framing publicly -- and building two or three non-identity
use cases into the v1 demo -- converts SolID from "identity protocol number N"
into infrastructure.

## 8. What the answer is to "is it going to outperform"

Honestly: with Phase 1 landed and ADR-0014 accepted, SolID has a real shot at
being the best Solana-native identity / attestation protocol. The architecture
is correct, the discipline is exceptional, and the competitive set on Solana
is thin.

To be the best protocol in ZK identity globally -- beating Polygon ID /
Privado ID / Semaphore / zkLogin on operational maturity -- the protocol
needs:

1. Phase 2 shipped (SEC-004, SEC-006, SEC-007, SEC-008, SEC-010 closed;
   revocation v1 wired; devnet deployed; 11 integration tests).
2. Phase 3 shipped (multi-party ceremony + formal verification + two external
   audits + mainnet deploy).
3. Phase 4+ at least partially shipped (recursive proofs OR WebGPU prover OR
   cross-chain verification OR SAS adapter -- pick two of four; any two give
   a moat).
4. The product layer built out (React hook + verifier facade + mobile SDK +
   issuer console + docs site).

Timelines: Phase 2 is 2-4 weeks of serious work. Phase 3 is 2-3 months
including audit. Phase 4 is open-ended but can start in parallel with
Phase 3 audit.

The protocol as it exists today is ~70-75 percent of a world-class v1. The
remaining 25-30 percent is well-scoped, has ADRs for the contentious
decisions, has CI harness landing to gate the fixes, and has a registry that
reads honestly.

Most protocols in this state are in much worse shape. Ship Phase 2 cleanly
and you are in the conversation. Ship Phase 3 cleanly and you are leading
the conversation.
