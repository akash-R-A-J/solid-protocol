### NF-01 (HIGH, MED-HIGH confidence) — Issuer-tree binding root is desynchronizable via stale caller-supplied path

**File:** `programs/issuer-registry/src/lib.rs:109-126` (helper), `:1664-1691` (revoke), `:1878-1901` (withdrawal), `:1437-1483` (append).

**Evidence.** `write_issuer_tree_binding_root` writes `new_root` and the current slot into the binding with **no monotonicity check** (compare `update_issuer_tree_root` at `:1263` which enforces `now_slot > last_slot`). The atomic ixs use this helper. They recompute the new Poseidon root from `compute_poseidon_merkle_root(&new_leaf, leaf_index, &caller_supplied_path)` (`:1672-1677`, `:1882-1887`, `:1464-1469`). The recompute proves the **path is internally consistent with the new leaf**, not that the **path siblings reflect the actual current tree state**.

**Attack scenario (high-confidence path):**

1. T=0: Issuer A registered, leaf at index 0; binding root = R0.
2. T=1: Issuer B registered, leaf at index 1; binding root = R1.
3. T=2: DAO calls `revoke_issuer_atomic` on A; binding root = R2 (A's leaf bumped).
4. T=3: B (in `Approved`) calls `request_withdrawal_atomic` with `old_root = R1` and a Poseidon path constructed against state-as-of-T=1.
   - SPL AC `replace_leaf` accepts because R1 is still inside SPL AC's concurrent-buffer window (~64 roots).
   - The on-chain Poseidon recompute consumes the same stale path, producing R3 = "state at T=1 with B's leaf bumped." R3 does **not** include A's revocation.
5. `write_issuer_tree_binding_root` writes R3 to the binding unconditionally.
6. A pre-revocation proof against issuer A now verifies: the witness commits to `issuerTreeRoot = R3` (in-circuit Merkle inclusion holds because R3 represents pre-revocation state), and the on-chain handler reads `IssuerTreeBinding.current_root = R3` and accepts.

**Net effect.** A's revocation is silently undone for proof verification, until another correctly-rooted update lands. The window collapses the moment any subsequent atomic ix uses a fresh path against the post-T=3 state, but the holder of the pre-revocation proof can race that.

**Why prior audits missed it.** SEC-045 closed the "binding does not update at all" gap. SEC-059 / H1 shipped the on-chain Poseidon recompute as integrity defense, but the recompute only proves path-vs-leaf consistency, not path-vs-current-state consistency. The 2026-04-29 synthesis treats "atomic + integrity-checked" as fully closed; the staleness vector is below its check.

**Proposed fix (no workaround).** Recompute *both* roots — the OLD root against `binding.current_root`, then the NEW root for the write:

```rust
// Before mutating, recompute OLD_ROOT against the OLD leaf via the same path.
let recomputed_old = compute_poseidon_merkle_root(&old_leaf, leaf_index, &path)?;
require!(recomputed_old == binding.current_root, ErrorCode::StaleProofPath);
// ... then bump leaf, recompute new root, write.
let recomputed_new = compute_poseidon_merkle_root(&new_leaf, leaf_index, &path)?;
write_issuer_tree_binding_root(binding, recomputed_new, Clock::get()?.slot)?;
```

This pins the path to the **binding's** root (which is monotonic by construction once NF-07 is also fixed), not to SPL AC's sliding window. Cost: one extra Poseidon-Merkle recompute (~50-80K CU). Doubles the existing CU cost on the path but eliminates the staleness window.

**Edge case considered and ruled out.** Could the attacker forge `old_leaf`? No — the leaf is structurally derived from the issuer pubkey + status, which the handler reads from the typed `IssuerAccount`, not from the wire.

**Regression gate.** New test `revoke_then_stale_withdrawal_atomic_rejected` in `programs/issuer-registry/tests/atomic_ix_state_monotonicity.rs` — drives the T=0..T=3 sequence above and asserts step 4 errors with `StaleProofPath`. Add a positive test `withdrawal_atomic_with_fresh_path_accepted` to confirm the legitimate flow still lands.

### NF-02 (HIGH, HIGH confidence) — `finalize_verification_key` is unreachable from any deploy script

**File:** `scripts/initialize.ts:421-512` (uploads chunks, never finalizes); `programs/zk-verifier/src/lib.rs:271-287` (the freeze-gate ix).

**Evidence.** `grep -rn 'finalizeVerificationKey\|finalize_verification_key' scripts/ ts-sdk/` returns zero matches. The on-chain ix exists but no off-chain caller exists.

**Effect.** Every deployment ends with `vk_initialized = true` and `vk_finalized = false`. In this state, the authority can call `store_verification_key` at any time with `chunk_index = 0` to **fully replace** the VK without the SEC-006 48-hour timelock — `store_verification_key` only refuses chunks while `vk_finalized == true` (`programs/zk-verifier/src/lib.rs:219`). The freeze-gate from SEC-006 Part 1 ("ADR-0015; on-chain freeze-gate + 48h rotation timelock"; registry SEC-006 marked Closed 2026-04-25) is the central mitigation against a compromised authority rotating to a malicious VK. **In production it has zero effect** because no system reaches the finalized state.

**Severity rationale.** This is not a *protocol-design* flaw (the on-chain primitive is correct); it is a *deployment-correctness* flaw that hollows out a HIGH-severity mitigation already counted as closed. The audit registry lists SEC-006 Part 1 as "landed 2026-04-25" — accurate for the on-chain code, but it never lands operationally.

**Proposed fix.** Append to `scripts/initialize.ts` after the chunk-upload loop completes:

```ts
console.log('   finalizing VK (SOLID-SEC-006)...');
await zkProgram.methods.finalizeVerificationKey().accounts({
  verifierConfig: verifierConfigPda,
  authority: wallet.publicKey,
}).rpc();

// Post-condition assertion.
const cfg = await zkProgram.account.verifierConfig.fetch(verifierConfigPda);
if (!cfg.vkFinalized) throw new Error('VK finalization failed; SEC-006 Part 1 inactive');
```

Add a parallel call to any cluster bootstrap script. Add a TS-SDK helper `freezeVerifierVk(connection, authority)` so future deploys cannot omit it.

**Regression gate.** New TS test `tests/integration/05_vk_freeze_required.ts` — runs `initialize.ts`, asserts `verifierConfig.vkFinalized == true`. Add a Rust test in zk-verifier confirming `verify_batch_proof` does *not* itself require `vk_finalized`, so users not running the new init path do not break (the assertion is on deployment correctness, not protocol).

### NF-03 (MEDIUM, HIGH confidence) — Schema-registry root updates have no on-chain integrity check

**File:** `programs/schema-registry/src/lib.rs:87-119` (`apply_schema_tree_root_update`), `:167-193` (`apply_global_root_update`).

**Evidence.** Both helpers write the caller-supplied `new_root` byte-for-byte after slot-monotonicity and authority checks. No `compute_poseidon_merkle_root` recompute is performed. Compare issuer-registry which does recompute (`programs/issuer-registry/src/lib.rs:1232-1238` and atomic ixs).

**Effect.** The recorded authority — a single signer (SEC-043 still open) — can post any 32-byte root as the active global / per-schema Poseidon root. A buggy off-chain pipeline (or a typo, or a partial state desync between an indexer and the script) silently corrupts the binding without a CPI to a tree program that would catch it. Verifier `verify_batch_proof` reads the binding's root as the source of truth (`programs/zk-verifier/src/lib.rs:491-495`, `:797-801`) and treats whatever is there as authoritative.

This is asymmetric defense-in-depth: issuer-registry pays ~50-80K CU per atomic ix to catch this exact class of error; schema-registry does not. The two stores feed the same circuit's public inputs and have the same blast radius.

**Why prior audits missed it.** The audits scrutinized the issuer-tree path post-ADR-0014 and noted the recompute as the SEC-059/H1 closure. The schema-tree binding lifecycle predates ADR-0014 and was treated as "in scope of the original SEC-019 fix" (which addressed schema-hash binding, not root-recompute integrity).

**Proposed fix.** Mirror the issuer-registry pattern. The schema-tree update ix should accept `(new_leaf, leaf_index, new_root, poseidon_path)` (the leaf is the credential commitment that triggered the update), recompute on-chain, and write only if `recomputed == new_root`. For the global tree, the "leaf" is the per-schema identity-state commitment that just changed. Cost: one extra ~50-80K CU recompute per update.

**Regression gate.** `apply_schema_tree_root_update_recompute_mismatch_rejected` host-side test. Plus an integration test `update_global_root_with_lying_authority_rejected` that drives the failing path.

### NF-04 (MEDIUM, MEDIUM confidence) — Cross-tx atomic-ix race writes inconsistent binding state

**File:** Same handlers as NF-01.

**Evidence.** Two atomic ixs in **different transactions** can both succeed if SPL AC's concurrent buffer accommodates both `old_root` values. Each writes its own Poseidon root to `IssuerTreeBinding.current_root` last-write-wins. There is no compare-and-swap on the binding root; only slot monotonicity in `update_issuer_tree_root` (and not even that in `write_issuer_tree_binding_root` — see NF-07).

This is the cross-tx form of NF-01 — same root cause but a different attack surface: rather than relying on a single attacker-supplied stale path, two well-formed-from-different-bases ixs interleave and the binding lands on whichever recompute came second, regardless of which represents the more-up-to-date state.

**Distinct from NF-01 because.** NF-01 is "attacker chooses stale base"; NF-04 is "scheduling race between two honest callers." The fix in NF-01 (require recompute against the binding's current root) closes NF-04 too — they are the same cure.

**Regression gate.** `concurrent_atomic_ixs_serialize_correctly` integration test that submits two atomic ixs in adjacent slots from two different DAO seats and asserts the second errors rather than both landing.

### NF-05 (MEDIUM, HIGH confidence) — `check_program_ids.py` does not validate TS-side program-ID consts

**File:** `scripts/check_program_ids.py`. Compare to `ts-sdk/packages/*/src/programIds.ts` (or equivalent), `ts-sdk/packages/verifier/src/index.ts:142-144` (`PROGRAM_IDS.zkVerifier`).

**Evidence.** The script reads `Anchor.toml`, `declare_id!()` literals, `crates/solid-light/src/cpi_helpers.rs` const literals, and `deployments/*.json`. It does **not** parse any TS file. A drift in `PROGRAM_IDS.zkVerifier` (or whatever ships under `@solid-protocol/sdk-config`) breaks `verify_batch_proof` ix builds end-to-end without surfacing in CI.

**Severity.** MEDIUM because TS-side drift surfaces immediately in any e2e run; not a silent cryptographic break. But the registry treats program-ID drift as load-bearing (SEC-032, SEC-040), and this gap means the gate is one-sided.

**Proposed fix.** Extend `check_program_ids.py` (or a sibling script) to grep TS files under `ts-sdk/packages/*/src/` for any `Buffer.from('...', 'base58')`, `new PublicKey('...')`, or `PROGRAM_IDS.{zkVerifier,issuerRegistry,schemaRegistry}` literal that resembles a base58 program ID, and validate against `Anchor.toml`. Add to CI's `.github/workflows/`. Strict allowlist: the only locations that may name a program ID literal are `programIds.ts` (or whichever module is canonical); other modules must import.

**Regression gate.** Add `tests/ci/test_program_id_typescript_drift.py` that fails when a TS file outside the canonical module names a base58 program ID inline.

### NF-06 (LOW, MEDIUM confidence) — `cooldown_ends_at` field reuse semantics are doc-only, not type-enforced

**File:** `programs/issuer-registry/src/lib.rs:1572` and `:1793`.

**Evidence.** `revoke_issuer_atomic` (Cooldown -> Revoked path) overwrites `cooldown_ends_at` with `now + 24h` (the dispute window), discarding the original 14-day cooldown timer. `request_withdrawal_atomic` sets it to `now + 14d`. The same `i64` field carries two distinct semantic meanings ("when cooldown ends" / "when dispute window ends"). The current code distinguishes by `issuer.status` — Cooldown vs Revoked. A future refactor that misreads the field, or a future status that carries its own deadline, will silently corrupt one of the two flows.

**Concrete near-miss path.** If the DAO revokes a Cooldown issuer at day 13 (1 day before cooldown ends), the dispute window is reset to (now + 24h), which lands at day 14. This may or may not match the operational intent — there is no doc that says "revoke shortens the wait, never extends it." A future expedited-revocation flow might dispute-window for 7 days; pasting that on top of an existing Cooldown timer is undefined.

**Proposed fix.** Split into two fields: `cooldown_ends_at: i64` and `dispute_window_ends_at: i64`. Make state-transition comments load-bearing in code: each handler asserts the fields it cares about, ignores the others. Adds 8 bytes to `IssuerAccount::SPACE` — bump and document the layout change in the same commit per CLAUDE.md "Hard invariants."

**Regression gate.** `revoke_during_cooldown_does_not_clobber_cooldown_window` test confirming that whichever field outlives the transition stays at its original value.

### NF-07 (LOW, HIGH confidence) — `update_issuer_tree_root` enforces slot monotonicity but `write_issuer_tree_binding_root` does not

**File:** `programs/issuer-registry/src/lib.rs:1263` vs `:109-126`.

**Evidence.** Pure code asymmetry. Two write paths to the same binding field; one enforces `now_slot > last_slot`, the other does not. The atomic ixs (calling `write_issuer_tree_binding_root`) pass `Clock::get()?.slot`, which is monotonic in practice within a single tx — but cross-tx, two atomic ixs in the same Solana slot would both succeed and both write, with the second winning. Today this is "harmless" only because SPL AC `replace_leaf` would reject the second CPI as redundant. As soon as SPL AC's concurrent semantics admit two same-slot updates (or a different leaf-presence ledger replaces it), the gap widens.

This is a precondition for NF-04's race surface, not an independent bug — but worth fixing in the same commit since it is a one-line addition.

**Fix.** Add `require!(slot > prev_slot, ErrorCode::IssuerTreeRootNotMonotonic)` inside `write_issuer_tree_binding_root` after parsing the existing `last_updated_slot`.

**Regression gate.** `write_issuer_tree_binding_root_rejects_non_monotonic_slot` host-side unit test.

### Categories with NO new findings

These were investigated and ruled out (note: "no finding" is itself an audit deliverable):

- **`PredicateEvaluator` operator range.** Although `operator` is unranged, out-of-range values produce `result = 0` deterministically (every `opIs[i]` IsEqual is false), so the proof is rejected, not silently bypassed. The doc comment on `predicate_evaluator.circom:7` is accurate and the soundness contract holds.
- **EdDSA-Poseidon S/R8 byte canonicality.** `Fr::from_le_bytes_mod_order` reduces non-canonical encodings, but the resulting field elements are equivalent for both verification and nullifier purposes. Malleability exists at the byte-encoding level but does not affect any public output (commitment, nullifier, leaf).
- **`MerkleInclusion.enabled` not bit-constrained internally.** `enabled * diff === 0` only skips the equality check for `enabled = 0`; any non-zero value still forces equality. Caller `IdentityAnchor` does enforce the bit constraint. No exploitable surface.
- **`numPredicates = 0` admittance.** Already tracked as SEC-051 (all-padding `[0,0,0,0]` proofs).
- **WASM bridge `&[u64]` data fields.** Bridge accepts u64 but circuit takes 254-bit field elements. Asymmetric — but the issuer is the trust boundary, not the bridge. Not a protocol bug.
- **`ProofBuffer` recovery from failed verify.** `upload_proof_chunk` allows in-place overwrite; users have a recovery path. Documenting it in the accounts struct doc-comment is a polish item, not a finding.

## 3. Part II — Architecture and robustness audit

This section preserves the full per-section findings from the architecture/robustness pass. Reviewed at HEAD `4892fb9` (post-`fb447ff`). Findings in the 04-25, 04-28, and 04-29 audits are not repeated except where state has changed since they were written.

### 3.1 Layer violations (L2)

#### 1.1 — TS SDK hard-codes a Groth16 instruction discriminator that the on-chain program already exports — MEDIUM

`ts-sdk/packages/issuer/src/index.ts:49-51` defines `ISSUE_CREDENTIAL_DISCRIMINATOR` as a literal 8-byte array with a doc-comment claiming `sha256("global:issue_credential")[..8]`. There is no test that recomputes this from the source string, no IDL-driven derivation, and no reference to `target/idl/issuer_registry.json`. Anchor already emits the canonical discriminator in the IDL the CI builds at `anchor idl build -p issuer_registry`. The same hand-rolled-bytes class produced **SEC-049** (`SPL_AC_REPLACE_LEAF_DISCRIMINATOR` was wrong and shipped latent because no integration test exercised the path).

**Fix.** Generate `ts-sdk/packages/<x>/src/discriminators.ts` from `target/idl/*.json` at build time. Add a CI lint that rejects PRs introducing `// = sha256("global:...")` literals without an adjacent recomputation test.

#### 1.2 — `tools/solid-prover/` is dead code masquerading as the production prover — MEDIUM

`tools/solid-prover/src/lib.rs:90` is the SEC-017 site (`test_rng()`). The 04-25 audit calls SEC-017 "trivial fix." It is worse than that: cross-referencing usage shows `tools/solid-prover` is **not invoked by any production path** — `scripts/prove.ts:324` and `ts-sdk/packages/holder/src/index.ts:264,743` use `snarkjs.groth16.fullProve`. The Rust prover exists but no script, SDK, or CI flow actually exercises it for proof generation — only `cargo test` exercises it. README.md:165 lists it as the "Native Groth16 prover via ark-circom"; ADR-0001 references it; the registry treats SEC-017 as a real proof-randomness leak. It is **architecture cosplay**: a published "production" component with no production callers.

This is risky for two reasons audits have not surfaced: (a) a contributor wiring `solid-prover` in a future mobile/uniffi flow inherits the `test_rng` and has no test that verifies two proofs over the same inputs differ; (b) it is a maintenance carrying-cost (separate workspace, separate `rust-toolchain.toml`, separate CI job, separate cargo cache) for code with no users.

**Fix.** Either *delete* it and remove all references (README, ADR-0001, Cargo workspace doc) — close SEC-017 as Won't Fix because the component is gone — or *promote* it to a published crate (`cargo publish`) used by an actual mobile-prover binary in the next session, with `OsRng` and a unique-nullifier round-trip test as the closure gate. The current half-state should not exist.

#### 1.3 — Off-chain `solid-light` recomputes on-chain SPL AC root via Keccak; on-chain reads it from header — HIGH

`crates/solid-light/src/cpi_helpers.rs:586-632` (`compute_concurrent_merkle_root_keccak`) is the SEC-045 closure helper. The 04-29 synthesis CRIT-2 already flagged this as unsound under SPL AC concurrent semantics. Beyond CRIT-2: this is a layer-violation pattern. On-chain code (`extract_active_root_from_concurrent_merkle_tree` at the same file:766) parses the SPL-AC header and reads `change_log[active_index].root`. Two separate paths, two separate trust assumptions, encode "what is the active SPL AC root" — the off-chain Keccak path-recompute, and the on-chain header parse. They will diverge under load.

**Fix.** Delete `compute_concurrent_merkle_root_keccak` once CRIT-2 is fixed — there is exactly one canonical "active root" reader and it lives in the on-chain handler (header parse). The SDK should never recompute it; it should fetch the post-CPI account, parse the header, and call it a day. Class-kill any function whose name contains `recompute_*_root`.

### 3.2 Type-safety gaps (L3)

#### 2.1 — `verify_batch_proof` / `verify_batch_proof_v2` accept five `UncheckedAccount`s the program already knows how to type — HIGH

`programs/zk-verifier/src/lib.rs:1190-1199` and `:1288-1297` declare `global_tree`, `schema_tree_0..3` as `UncheckedAccount<'info>`. The handler does an in-handler owner-check (line 487, 546, 793, 832), but Anchor seed-binding is left off. The 04-29 synthesis M4 names *one* of these (`global_tree`); the gap is broader.

`schema_tree_0..3` are documented as "per-schema tree metadata PDA" owned by `schema_registry`. They have a deterministic seed — the schema hash is the public input, so the PDA seeds *are* derivable. Yet the handler reads the schema hash from the account body and hopes the caller did not swap accounts.

**Concrete attack the synthesis did not articulate at this depth:** a malicious caller can submit `verify_batch_proof` with `schema_tree_2` and `schema_tree_3` set to *the same account* (the same `SchemaTreeBinding` PDA). The owner-check at `:546` passes (both are owned by schema-registry). The handler iterates on `[count]` indices and, for inactive slots, does not care — but the slot-population logic at `:538-541` reads each `schema_tree_i.data` independently. If both pointers alias the same data, the proof's `merkleRoots[2]` and `[3]` get the same root — perfectly legal in the witness, and now the prover's "I have one credential under schema A, one under schema B" claim is collapsed without any constraint catching it.

This is mostly defense-in-depth (the in-circuit `IdentityAnchor` derived per-schema BJJ key still ties a credential to its schema), but the alias removes a layer. Anchor has the tool for this: `seeds = [SCHEMA_TREE_BINDING_SEED, schema_hash.as_ref()], seeds::program = SCHEMA_REGISTRY_ID`.

**Fix.** Type all five accounts. Promote `global_tree` to `Account<'info, GlobalStateBinding>` (the schema-registry struct), and `schema_tree_i` to `Account<'info, SchemaTreeBinding>` with seed-binding to the schema hash already on the wire. The handler's hand-rolled owner-check disappears (Anchor enforces it via the typed account). Result: the four-pointer-aliasing class becomes a compile-time impossibility.

#### 2.2 — `revoke_issuer_atomic` and `request_withdrawal_atomic` accept `old_root: [u8; 32]` and `Vec<u8>` proof-path — MEDIUM

`programs/issuer-registry/src/lib.rs:1535-1536, :1742-1745`. The H2 finding (synthesis) notes the missing `old_root == binding.current_root` pre-check. Beyond that: typing both as raw bytes is the L3 pattern — a typed seed-derived `old_root` would not need a runtime check at all. The SPL AC contract is what it is; we cannot change its CPI shape. But the *handler arg* does not have to be a free `[u8; 32]` — it can be parsed from `binding.current_root` directly and removed from the ix surface entirely. Stale-root replay then becomes structurally impossible because the caller has no `old_root` knob to turn.

**Fix.** Drop the `old_root` arg. Read it from the binding. The SDK loses the ability to "lie" about the old root; the wire shape shrinks 32 B; the test surface shrinks. (Note: this fix is implicit in the NF-01 fix — both touch the same path.)

#### 2.3 — `update_issuer_tree_root(new_root: [u8;32])` is a typed-bytes injection point — HIGH (covered as H1/SEC-059 by synthesis)

Already flagged in synthesis H1. The 04-30 commit `fb447ff` claims H1 is closed (handler comment at `programs/issuer-registry/src/lib.rs:1172,1346,1448` references SEC-059 closure). Verify by reading the handler. The deprecation path the synthesis recommended (delete the ix entirely and add `reconcile_issuer_tree_root(merkle_tree)` that derives the root from header) is the structurally-correct fix; if the closure landed something narrower, this is still half-shut.

### 3.3 Atomicity gaps (L3)

#### 3.1 — `IssuerTreeBinding` and the SPL AC tree it binds are not born together — HIGH

The IssuerTreeBinding singleton is initialized by one ix (`initialize_issuer_tree_binding`); the SPL AC `merkle_tree` account is initialized by SPL AC's own `init_merkle_tree` ix in a separate tx. There is a window where the binding exists with `current_root = [0u8;32]` (or the empty-tree root) but the merkle_tree account does not yet exist, or vice-versa. During this window the verifier accepts proofs whose `issuerTreeRoot` matches whatever was written, regardless of whether the tree the SDK is building proofs against is the same tree.

**Fix.** Birth the SPL AC tree CPI inside the same Anchor handler that initializes `IssuerTreeBinding`. Use `init_if_needed` on the binding only if the tree CPI has succeeded; on failure the whole tx rolls back and neither account exists. Same pattern the synthesis recommended for `revoke_issuer_atomic`.

#### 3.2 — `SchemaTreeBinding`-N and `GlobalStateBinding` cross-ref each other but do not co-init — MEDIUM

Tracing `register_schema -> initialize_tree_binding -> initialize_global_binding`: each ix is independent, so a partially-initialized state is visible (schema registered, tree binding missing, global binding missing). The verifier's `schema_tree_0..3` slot-fill at `programs/zk-verifier/src/lib.rs:538-541` does not require all four slots to be live — inactive slots are tolerated. So a partial-init schema is *queriable* before its global binding exists, with undefined semantics on `merkleRoots[i]`.

**Fix.** Compose `register_schema` to take the global-binding account in `remaining_accounts` and CPI-call `initialize_tree_binding` inside it. The schema registration then either fully exists (atomic) or does not.

### D. SOLID-SEC-043 — `IssuerTreeBinding` operator multisig

**STATUS — Open.** Single-key today.

**RECOMMENDATION — three-role split, NOT raw Squads 3-of-5.** Reasoning:

- Squads alone is multi-sig of one privilege class, but the current `registry_config.authority` gates ~6 distinct privileges (rotation, append, revoke, freeze, slash, emergency). Multisig reduces frequency of catastrophic compromise; it does NOT reduce blast radius.
- Three roles bound to three thresholds + timelocks:
  - **Rotation Authority** — VK rotation, schema-tree-binding rotation, registry-config rotation. 5-of-7 multisig + 7-day timelock.
  - **Operator Authority** — `append_issuer_leaf`, atomic revoke/withdrawal. 3-of-5 multisig, 24h timelock for revoke, 0h for routine append.
  - **Emergency Authority** — `set_issuer_tree_binding_status` (freeze), `slash_issuer`. Separate signer set. 24h challenge window for slash; instant freeze (with 1h timelock for non-emergency-freeze, 0h for declared emergency).
- ADR-0016 territory. Squads-as-implementation under each role.

**MIGRATION.**

1. Introduce `OperatorAuthority`, `RotationAuthority`, `EmergencyAuthority` PDAs each storing a multisig threshold and member set.
2. New ix `transfer_authority_v2(role, new_pda)` with two-step propose/accept (closes SEC-016 simultaneously).
3. Existing `IssuerTreeBinding.stored_authority` field renamed -> `operator_authority_pda`. Replace pubkey check with PDA-signer check via `is_pda_signer(operator_authority_pda)` helper that confirms (a) account is a PDA owned by the multisig program, (b) its signer threshold was satisfied for this ix.
4. Bootstrap: existing single-signer entries migrate via a one-shot `migrate_to_multisig(current_authority_signs)` that consumes the old key once.

**UPGRADE-AUTHORITY QUESTION.** Solana program-upgrade authority is separate from in-program authority. The three-role split applies to in-program privileges; the program-upgrade authority should ALSO be a 5-of-7 multisig (Rotation Authority is the obvious candidate). Document explicitly in CLAUDE.md hard invariants.

**REGRESSION GATE.** Unit + integration tests as documented.

### F. SOLID-SEC-051 — all-padding `[0,0,0,0]` admittance

**STATUS — Open.** Single-constraint fix prepared. Defers to next setup cycle.

**CIRCUIT FIX (one constraint).**

```circom
// circuits/batch_credential_query.circom STEP 0 (early in main template)
component anySchemaSet = IsZero();
anySchemaSet.in <== schemaHashes[0];
anySchemaSet.out === 0;  // require slot 0 active
```

Combined with SEC-050's padding-canonicality (active prefix + zero suffix), this enforces: at least one active slot at position 0, plus sorted active prefix, plus zero suffix.

**ON-CHAIN DEFENSE-IN-DEPTH (defer-with-justification).** Recommend NOT adding a handler-level reject. Reasoning:
- The circuit's "skip zero schema slots" at `programs/zk-verifier/src/lib.rs:500-502` exists to support legitimate `K < NUM_CREDS` queries (a holder with 2 credentials proving against a 4-slot circuit pads slots 2,3 to zero).
- A handler reject of `schema_hashes[0] == [0u8; 32]` would close SEC-051 at the cost of breaking the legitimate single-credential case where the holder happened to receive their only credential bound to no schema (structurally impossible today, but a policy flip in the future could allow).
- The right shape is **circuit-level** invariant — at least one ACTIVE slot. Handler stays permissive; circuit becomes restrictive.

**SETUP COUPLING.** Lane B / next ceremony.

**REGRESSION GATE.** Witness-tester case `all_padding_rejected.test.js`:
- Positive: one active slot, three padding -> admit.
- Negative: all-zero schema slots -> witness-build fails.
- Property: enumerate all 16 active-mask combinations on a 4-slot circuit, assert exactly the 15 non-empty masks are admitted.

**RISK if deferred.** "At least one credential held" is not a circuit-level invariant today. Any future verifier integration that interprets a passing proof as "holder owns ≥1 credential" is wrong.
