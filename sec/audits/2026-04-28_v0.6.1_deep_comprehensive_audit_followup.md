Date: 2026-04-28

Scope: Full-system follow-up on core trust boundaries (circuits, on-chain programs, SDK/wire, CI/integration posture)

---

## Executive Verdict

The system is substantially hardened versus earlier versions, and multiple high-risk issues are closed in code. The core soundness model (circuit constraints + on-chain owner/binding checks + nullifier replay protection) is materially improved.

However, the protocol is **not fully integrated end-to-end yet**:

1. The on-chain proof submission path remains blocked by instruction wire size (B13 class issue).
2. The documented integration suite 02..11 is not implemented in-repo yet.
3. Several OPEN security items remain (including one HIGH mainnet blocker and trusted-setup process risk).

Therefore: robust direction, but not production-complete.

## Confirmed Findings (This Follow-up)

Only findings with direct evidence in current source/docs are listed.

### [HIGH] AUDIT-2026-04-28-001: Proof submission wire-size overflow still blocks full on-chain integration

Confidence: 10/10
Category: Integration availability / protocol execution path
Locations:
- `ts-sdk/packages/verifier/src/index.ts`
- `docs/E2E_BLOCKERS.md` (B13)
- `plan/RESUME.md`

Description:
The verifier SDK instruction builder still serializes a full 32x32-byte public input vector plus proof and metadata, yielding 1324-byte instruction data before transaction framing. This exceeds Solana legacy transaction packet constraints for the intended submission flow.

Evidence:
- Builder comment and allocation are explicit:
  - `1324 bytes` total layout in verifier SDK.
  - Buffer size computed as `8 + 64 + 128 + 64 + 4 + NR_PUBLIC_INPUTS * 32 + 32`.
- Blocker doc states the same overflow class and runtime failure signature.

Impact:
Even with valid Groth16 witness/proof generation, the final "submit verify_batch_proof on-chain" stage is blocked. This prevents complete E2E success semantics.

Recommended remediation:
Implement the already-documented approach:
- Reconstruct redundant public inputs on-chain from passed accounts.
- Shrink transmitted public inputs from 32 to 21 slots (save 352
  bytes; total ix data shrinks 1324 -> 972 bytes). The 11
  reconstructible slots are 1 (globalRoot), 2..5 (merkleRoots),
  6..9 (schemaHashes), 10 (issuerTreeRoot), and 29
  (verifierAddress). Slots 30 (verifierNonce) and 31
  (currentTimestamp) stay on the wire because they are
  witness-bound and Groth16 enforces polynomial-equality on
  public inputs with zero tolerance; the SEC-005 skew window
  wraps the wire-supplied currentTimestamp on-chain but does not
  replace the cryptographic equality. Earlier copies of this
  audit and the plan/blocker docs claimed "12 reconstructible /
  384 bytes saved / 1324 -> 940" -- that math was off by one
  slot (currentTimestamp); corrected 2026-04-28 in this audit,
  `docs/E2E_BLOCKERS.md` B13, `plan/IMPLEMENTATION_PLAN.md`
  Appendix D, `plan/RESUME.md`, and `CLAUDE.md`.
- Keep circuit/on-chain index contract explicit and tested.

Priority: P0

### [MEDIUM] AUDIT-2026-04-28-002: Integration test suite contract is materially incomplete vs documented coverage

Confidence: 10/10
Category: Security regression assurance / integration hardening
Locations:
- `tests/integration/README.md`
- `tests/integration/`
- `package.json` (root)

Description:
The integration README states a multi-scenario suite (`01..11`), but repository contents currently include only `01_registry_init.test.ts` and no root integration test script. This creates a testing-coverage gap against documented security regression goals (revocation, forged roots, replay, expiry, cross-language vectors inside integration run).

Evidence:
- `tests/integration/README.md` table lists `02..11`.
- Actual files in `tests/integration/`: only `01_registry_init.test.ts` and `README.md`.
- Root `package.json` has no `test:integration` script.

Impact:
Critical cross-program and adversarial-path regression checks are not enforceable through the claimed integration harness.

Recommended remediation:
- Implement tests 02..11 as documented.
- Add canonical root script (`test:integration`) and CI gate alignment.
- Treat scenario coverage as load-bearing release criteria.

Priority: P1

---

### [MEDIUM] AUDIT-2026-04-28-003: GitHub Actions are pinned to mutable tags rather than immutable SHAs

Confidence: 9/10
Category: Supply-chain / CI integrity
Location:
- `.github/workflows/ci.yml`

Description:
Workflow actions are referenced with mutable tags (`@v4`, `@v1`, `@v5`) instead of full commit SHAs.

Evidence:
- Multiple uses in CI file: `actions/checkout@v4`, `actions/cache@v4`, `actions/setup-node@v4`, etc.

Impact:
Upstream tag retargeting or compromised action release could alter CI behavior without repository changes.

Recommended remediation:
- Pin third-party actions to immutable commit SHAs.
- Maintain periodic action bump PRs with explicit diff review.

Priority: P1
